# Hcomm AIV RoCE Batched WriteNbi/ReadNbi Sample

## Overview

This sample uses MPI to manage multiple processes. Each MPI rank selects one NPU and validates the
batch interfaces provided by `hcomm_aiv_roce.h` over a `COMM_PROTOCOL_ROCE` channel:

- `MakeBatchHandle`
- `WriteNbi` with a `UbcBatchHandle` argument
- `ReadNbi` with a `UbcBatchHandle` argument
- `BatchCommit`
- `Drain`

Rank i communicates with rank i + N/2, where N is the total rank count:

- 2 ranks: rank 0 ↔ rank 1
- 4 ranks: rank 0 ↔ rank 2, rank 1 ↔ rank 3
- 8 ranks: rank 0 ↔ rank 4, rank 1 ↔ rank 5, rank 2 ↔ rank 6, rank 3 ↔ rank 7

Each rank connects only to its unique peer. One batch handle receives 1000 `WriteNbi` calls and
1000 `ReadNbi` calls. The `i`th call uses an address offset of `i * 64` bytes. After the batch is
committed and drained, each rank validates the 1000 slices written by the peer and the 1000
slices read back from the same peer.
All WQEs except the last `WriteNbi` and the last `ReadNbi` use the `cqe=0` configuration to
suppress completion events. Those two operations use the default config template parameter,
whose `cqe` is `1`, so the whole 2000-WQE batch produces two CQEs. The `PollCq` inside `Drain`
waits for only those two completion events.

## Data Layout

Each rank registers a `3 * 1000 * 64` byte communication buffer:

| Region | Purpose |
| --- | --- |
| `[0, 64000)` | Source data owned by this rank |
| `[64000, 128000)` | Results written by the peer |
| `[128000, 192000)` | Results read from the peer |

The batch WQE buffer lives in the Kernel VECOUT UB and contains `2000 * 64` bytes.

## Build

Source the CANN environment and build from this directory:

```bash
cd examples/aicore/hcomm/08_hcomm_roce_batch_write_read
source ${install_path}/cann/set_env.sh
export MPI_HOME=/usr/local/mpich
mkdir build
cd build
cmake -DCMAKE_ASC_ARCHITECTURES=dav-3510 ..
make -j
```

To enable `ASCENDC_DEBUG`, use `cmake -DCMAKE_ASC_ARCHITECTURES=dav-3510 -DASCENDC_DEBUG=ON ..`.

An MPI C++ compiler (`mpicxx`) is required to build this sample.

## Enable MPI Environment Variables

Adjust the following settings according to the actual MPI installation path.

```bash
export MPI_HOME=/usr/local/mpich
export PATH="${MPI_HOME}/bin:${PATH}"
export LD_LIBRARY_PATH="${MPI_HOME}/lib:${LD_LIBRARY_PATH:-}"
```

## Run

On a multi-NPU host, start one MPI process per NPU. Rank `i` uses NPU `i`, and the rank count must be an even number greater than or equal to 2:

```bash
cd examples/aicore/hcomm/08_hcomm_roce_batch_write_read
source ${install_path}/cann/set_env.sh
mpirun -n 4 $(pwd)/build/hcomm_roce_batch_write_read
```

The RoCE links between the NPUs must be available, and the MPI ranks must not exceed the number of
available NPUs. On success, the sample prints:

```text
[rank 0] hcomm_roce_batch_write_read | peer=2 WriteNbi=1000 ReadNbi=1000 | PASS
[rank 1] hcomm_roce_batch_write_read | peer=3 WriteNbi=1000 ReadNbi=1000 | PASS
[rank 2] hcomm_roce_batch_write_read | peer=0 WriteNbi=1000 ReadNbi=1000 | PASS
[rank 3] hcomm_roce_batch_write_read | peer=1 WriteNbi=1000 ReadNbi=1000 | PASS
RESULT | Example=hcomm_roce_batch_write_read | Status=PASS
```

## Notes

- Running the sample requires at least two NPUs; the rank count must be even and must not exceed the available NPU count.
- The channel must use COMM_PROTOCOL_ROCE, matching `Hcomm<COMM_PROTOCOL_ROCE>` on the kernel side.
- MPI Bcast distributes the root info generated by HcclGetRootInfo to all ranks.
- The 1000 WriteNbi and 1000 ReadNbi calls are submitted through one batch handle; only the last WriteNbi and the last ReadNbi use the default config and request CQEs, and data is validated only after Drain returns.
- Each rank creates a channel only to rank i + N/2, and the write and read results are validated against the same peer.
