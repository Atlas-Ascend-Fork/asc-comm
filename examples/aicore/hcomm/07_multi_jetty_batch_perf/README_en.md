# Multi-Jetty SIMT Engineering Acceptance Case

This case relies on Hcomm internal completion-management interfaces and is for engineering acceptance, not a user API call example. It uses the Hcomm headers installed under `$ASCEND_HOME_PATH`. Before running, install the run package that matches this repository's source code, and compile the case with `--clean`.

The case demonstrates concurrent publication from multiple Jettys, and one consumer that uniformly handles the shared CQ and advances the completion state of each Jetty by JFS ownership. Write, Read, and WriteWithNotify are supported.

MakeBatchHandle and every batch Write/Read/Notify explicitly pass a group. The same handle uses a fixed Group and a fixed UB workspace. The publication flow includes three barriers, and the shared CQ is uniformly managed by one consumer.

## Execution

```bash
# The CANN environment has been loaded. Build only one batch of VFs at a time.
bash build.sh --batch-size 1
# By default, run Write/Read/Notify x J1/2/4/8, 12 items in total.
bash run.sh --batch-size 1
# Optionally run one item.
bash run.sh --batch-size 1 --api write --jetty-counts 4
# Repeat the two commands above for 8, 32, 64, 128, and 256, six groups with 72 items in total.
```

Fixed geometry: 64B, 1024 timed requests per Jetty, 96 warmup requests aligned upward to the batch size, and two devices. `--batch-size` specifies both the request count per batch and the lane count per Jetty, with one request per lane. `--jetty-counts` specifies the Jetty count; the lane count and the per-lane request count cannot be configured independently.

Each group has its own build directory `build/simt-matrix-bs<N>` and compiles exactly one parallel VF. `build.sh` sets a 300-second limit for CMake configuration and compilation; the build fails when the limit is exceeded. After a successful build, the script reads the VF resource record for the corresponding batch/Jetty geometry, requires the stack size to be no greater than 1152B, and records the register usage. `--clean` removes only the selected artifacts.

Before running, verify `Layout=matrix-v4`, the batch size, and the binary SHA generated by the build. Incremental builds reuse resource records only when the object SHA is the same. Build and execution parameters are documented in the `--help` output of each script.

## File Responsibilities

| File | Responsibility |
|------|----------------|
| main.cpp | Buffer allocation, kernel launch, result collection, and resource release |
| host_setup.h | Jetty creation and remote-memory index resolution |
| simt_kernel.cpp | Single parallel VF with warmup/timing/Drain flow |
| simt_submit.h | Three-barrier publication sequence and per-lane SQ maintenance |
| simt_completion.h | CompletionSet init/continuation, window registration, and completion snapshot |
| validation.h | Completion counts, all payload bytes, and Notify value validation |
| multi_jetty_batch_perf_common.h | Shared constants and host/device data layout |

Each lane maintains the SQ it constructs, and publishers of multiple Jettys publish concurrently. Three block barriers coordinate before publication, after publication, and at the start of the next batch; groups wait at these boundaries. The shared-CQ single-consumer rule only constrains completion management and does not require Jettys to submit in turn. J8/BS256 uses two kernels in the same stream, each containing four Jettys; the second kernel continues the same CompletionSet without clearing the CQ cursor. The output uses Jettys and ConcurrentJettys to distinguish the configured count from the actual maximum concurrency.

## Results

Each item requires both process success, completion-count PASS, and data validation on the corresponding side; Notify also requires all notification values to pass. Read checks the initiator, and Write/Notify check the receiver, including warmup data.

Each group produces 12 RESULT lines and one MATRIX_SUMMARY. Full per-rank logs are kept in the `.ranks.*` directory next to the summary log. Ordinary validation failures collect the rest of the group; timeouts, signals, and initialization errors stop the remaining items. A combination that was not executed cannot be counted as PASS.

It uses the same output fields as simt_batch_perf: API, Mode, DataSize/B, BatchSize, Jettys, ConcurrentJettys, IssueTicksPerRequest, Pair, and Status. The primary metric is the per-request issue cost IssueTicksPerRequest, using raw clock() ticks, which includes the submission-path synchronization and excludes the subsequent Drain wait. Multiple kernels accumulate the submission interval and exclude host launch gaps. Normal runs do not expand the completion snapshot and validation details; all checks still execute, with the details kept in the rank logs and printed only on failure. Before the clock units are aligned, do not directly compute the speedup against archived SIMD.

## RESULT Fields

| Field | Meaning |
|-------|---------|
| API | Communication operation, such as write, read, or notify |
| Mode | Immediate = single-lane direct submission; ExplicitBatch = single-lane explicit Batch; GroupBatch = multiple lanes cooperating on one Jetty; MultiJetty = concurrent multi-Jetty case |
| DataSize/B | Data bytes per request, excluding control information such as the Notify flag |
| BatchSize | Request count per Jetty per batch; GroupBatch/MultiJetty construct one item per lane, so it also equals the lane count per Jetty |
| Jettys | Total configured Jetty count for the rank pair |
| ConcurrentJettys | Maximum number of Jettys participating in submission in a single kernel; for J8/BS256 it is 4, requiring two kernels |
| IssueTicksPerRequest | Total ticks in the submission timing interval divided by the total request count; smaller is better. Raw clock() count, not converted to ns |
| Pair | Communicating rank pair, for example 0-1; four pairs with eight cards |
| Status | Whether execution on both ends and the correctness checks for the case pass; PASS or FAIL |

IssueTicksPerRequest measures the average issue cost, not the end-to-end latency of a single request. It includes construction/publication and submission-path synchronization, and excludes the subsequent Drain wait. It excludes warmup, and multiple kernels accumulate the submission interval and divide it by the total request count, also excluding host launch gaps.

Successful builds do not print the compilation process; normal runs print only the RESULT lines and existing summaries. The compilation output is saved in build-output.log under the build directory, and the run configuration is recorded in the `.metadata` file next to the summary log. On failure, the last 40 lines of the compilation log or the corresponding rank log are shown automatically; these files do not need to be relayed on success.
