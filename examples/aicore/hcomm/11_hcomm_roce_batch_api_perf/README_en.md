# Hcomm AIV RoCE Batch API Performance Example

## Overview

This example is adapted from 09_hcomm_roce_batch_write_read to measure the RoCE batch APIs at different payload sizes. By default, it runs the complete WriteNbi flow with payloads starting at 256 bytes and doubling up to 256 MB. Use --api read to run the complete ReadNbi flow.
Requests in one batch do not overlap: request i uses an offset of i * AlignUp(dataSize, 64) bytes.

Each round contains these phases:

1. MakeBatchHandle
2. WriteNbi or ReadNbi 10 times; the first 9 requests use cqe=0 and the 10th uses cqe=1
3. BatchCommit
4. Drain

The 10th request generates the only CQE in the batch, so Drain waits for all 10 requests.

The device records issue time per request, BatchCommit, Drain, and total elapsed time in cycles. The host records elapsed time from kernel launch through aclrtSynchronizeStream in nanoseconds; issue time per request is the batch issue time divided by the batch size.

## Data Layout

At startup, the example calculates, allocates, and registers one contiguous communication memory region from --max-bytes and --batch-size; the registered region is at least 4 KB. --min-bytes and --max-bytes are configurable within the range from 256 bytes to 256 MB, and the registered memory size adapts to --max-bytes. The send buffer starts at the region base, and the receive buffer starts after the 64-byte-aligned request span. Requests use payload-sized slots aligned up to 64 bytes based on the initial registered address; no request registers a new memory region.
The total registered size is max(4096, 2 * batchSize * AlignUp(maxBytes, 64)). The first half is the send region and the second half is the receive region. Both regions contain batchSize request slots of AlignUp(maxBytes, 64) bytes each. For WriteNbi, a local send slot is the source and the peer receive slot is the destination. For ReadNbi, a local receive slot is the destination and the peer send slot is the source. Requests in one batch advance by AlignUp(dataSize, 64) bytes based on the initial registered address; no request registers a new memory region.
The send region is filled with a data pattern that varies by rank and address offset, which detects requests landing in the wrong slot or data being shifted.

## Build

```bash
cd examples/aicore/hcomm/11_hcomm_roce_batch_api_perf
source `CANN install path`/set_env.sh
export MPI_HOME=/usr/local/mpich
mkdir build
cd build
cmake -DCMAKE_ASC_ARCHITECTURES=dav-3510 ..
make -j
```

To enable `ASCENDC_DEBUG`, use `cmake -DCMAKE_ASC_ARCHITECTURES=dav-3510 -DASCENDC_DEBUG=ON ..`.

An MPI C++ compiler (mpicxx) is required.

## Enable MPI Environment Variables

Adjust the following settings according to the actual MPI installation path.

```bash
export MPI_HOME=/usr/local/mpich
export PATH="${MPI_HOME}/bin:${PATH}"
export LD_LIBRARY_PATH="${MPI_HOME}/lib:${LD_LIBRARY_PATH:-}"
```

## Run

```bash
cd examples/aicore/hcomm/11_hcomm_roce_batch_api_perf
source `CANN install path`/set_env.sh
mpirun -n 2 `sample build directory`/hcomm_roce_batch_api_perf 2>&1 | tee run.log
```

Optional arguments:

```bash
mpirun -n 2 `sample build directory`/hcomm_roce_batch_api_perf \
  --api write --batch-size 10 --min-bytes 256 --max-bytes 268435456 2>&1 | tee run.log
```

The output contains one PERF_DATA record per rank, API, and payload size:

```text
    PERF_DATA | Rank=0 | API=WriteNbi | DataBytes=256 | BatchSize=10 | IssuePerRequest(Cycles)=... | Commit(Cycles)=... | Drain(Cycles)=... | TotalDevice(Cycles)=... | Host(Ns)=... | DeviceGBps=...
RESULT | Example=hcomm_roce_batch_api_perf | Status=PASS
```

Valid values for --api are write and read. The default is write.

## Export Results

Convert the run log to a CSV table:

```bash
python3 parse_perf_data.py --csv run.log
```

This creates perf_data.csv in the current directory by default.

## Notes

- At least two NPUs are required, and the rank count must not exceed the available NPU count.
- The channel must use COMM_PROTOCOL_ROCE, matching `Hcomm<COMM_PROTOCOL_ROCE>` on the kernel side.
- MPI Bcast distributes the root info generated by HcclGetRootInfo to all ranks.
- A full default run registers 5 GB of contiguous device memory on each rank (2.5 GB for send and 2.5 GB for receive). When --max-bytes specifies a smaller upper bound, the registered memory shrinks accordingly.
- All communication addresses must be 64-byte aligned.
- After both WriteNbi and ReadNbi complete, the first min(dataSize, 256) bytes of each request slot are validated. Local receive slots are cleared before ReadNbi to prevent stale data from affecting validation.
