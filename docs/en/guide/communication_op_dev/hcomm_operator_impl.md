# Hcomm-Based Communication Operator Development Guide

<!-- md-trans-meta sourceCommit=5ed547c8af0b4fe59c907ddcd1d49348087706f5 translatedAt=2026-11-05T01:37:04.685Z pushedAt=2026-11-09T06:49:19.127Z nl=2 -->

## Overview

Hcomm is a point-to-point communication API on the AI Core side. It selects the communication protocol through the `AscendC::Hcomm` template and provides one-sided data plane capabilities such as `WriteNbi`/`ReadNbi`/`WriteValueNbi`/`WriteWithNotifyNbi`/`WriteReduceNbi` (write task with reduction)/`AtomicFAA`/`AtomicCAS`, as well as `Commit`/`Drain` submission and completion semantics. Hcomm works based on explicit `ChannelHandle` communication channels and registered memory: developers obtain the peer link and create a channel through the HCCL (Huawei Collective Communication Library) API, and the kernel side directly submits read/write tasks using the remote address of the peer's registered memory.

This guide uses AllGather as an example to introduce the complete development flow of Hcomm communication operators. AllGather aggregates the local shard of each rank to all ranks in the communicator: each rank writes its local shard to the corresponding offset of every other peer's buffer through `WriteNbi`. After the communication completes, the buffers of all ranks hold the full data arranged by **rankId**.

## Supported Scope

| Item | Description |
| --- | --- |
| Communication protocol | Supports `COMM_PROTOCOL_UB_CTP` and `COMM_PROTOCOL_ROCE`. For the specific APIs supported by each protocol, see [AI Core Hcomm API](../../api/aicore/hcomm/README.md) |
| Communication engine | `COMM_ENGINE_AIV` |

## Overall Process

Hcomm communication operator development is divided into two stages: control plane resource preparation and data plane communication execution.

Control plane process:

1. Initialize the operating environment.
2. Create a communicator.
3. Allocate memory and register communication memory.
4. Obtain the peer link and create a channel.
5. Obtain the peer registered memory.
6. Deliver the channel and memory address to the kernel.
7. Destroy communication resources.

Data plane process:

1. Perform preprocessing.
2. Submit the communication task.
3. Wait for completion.

## Control Plane Resource Preparation

### Initializing the Operating Environment

  ```cpp
  uint32_t rank;      // Current rankId
  uint32_t nranks;    // Total number of ranks
  aclInit(nullptr);
  aclrtSetDevice(static_cast<uint32_t>(rank));
  aclrtStream stream = nullptr;
  aclrtCreateStream(&stream);
  ```

### Creating a Communicator

All ranks in a communicator must share the same **rootInfo** to create the domain (see [`HcclGetRootInfo`](https://gitcode.com/cann/hcomm/blob/master/docs/en/api_ref/comm_mgr_c/HcclGetRootInfo.md) and [`HcclCommInitRootInfo`](https://gitcode.com/cann/hcomm/blob/master/docs/en/api_ref/comm_mgr_c/HcclCommInitRootInfo.md)). The Hcomm flow creates the communicator through `HcclCommConfig` and sets `hcclWorldRankID` to the current global rank. For the corresponding APIs, see [`HcclCommConfigInit`](https://gitcode.com/cann/hcomm/blob/master/docs/en/api_ref/comm_mgr_c/HcclCommConfigInit.md) and [`HcclCommInitRootInfoConfig`](https://gitcode.com/cann/hcomm/blob/master/docs/en/api_ref/comm_mgr_c/HcclCommInitRootInfoConfig.md).

The sample project exchanges **rootInfo** through a TCP socket control channel centered on rank 0. For details, see `examples/aicore/utils/rank_sync.h` and `examples/aicore/utils/hccl_comm_init.h`. Other methods such as file exchange can also be used: the root node writes **rootInfo** to a file in a shared path, and other ranks read the same **rootInfo** after the file is ready.

  ```cpp
  // Control channel endpoint (passed from the command line), in the format "tcp://ip:port"
  std::string ctrlEndpoint;
  // Establish the TCP control channel: rank 0 listens on the endpoint, and the other ranks connect.
  examples::RankSyncContext sync = rank == 0U ? examples::RankSyncContext::Listen(ctrlEndpoint, nranks) :
                                                examples::RankSyncContext::Connect(rank, nranks, ctrlEndpoint);

  // Configure the communicator creation parameters.
  HcclCommConfig config;
  HcclCommConfigInit(&config);
  config.hcclWorldRankID = rank;

  // Generate the rank identifier information of the root node: generated by the root node, and all ranks in the communicator must share the same rootInfo.
  HcclRootInfo rootInfo = {};
  if (rank == 0) {
      HcclGetRootInfo(&rootInfo);
  }
  // Exchange rootInfo through the control channel AllGather, and all ranks use the rootInfo of rank 0.
  std::vector<HcclRootInfo> allRootInfo(nranks);
  sync.Allgather(examples::kTagRootInfo, &rootInfo, sizeof(rootInfo), allRootInfo.data());
  // All ranks use the same rootInfo to create the communicator.
  HcclComm hcclComm;
  HcclCommInitRootInfoConfig(nranks, &allRootInfo[0], rank, &config, &hcclComm);
  ```

### Allocating Memory and Registering Communication Memory

In the AllGather scenario, the communication buffer must accommodate `nranks` shards: the local shard is pre-placed at the `rankId * SHARD_SIZE` offset and serves as the source data that the kernel side writes to each peer; this buffer also serves as the AllGather result buffer, receiving the shards written by the other ranks.

Allocate the communication buffer, and register the local buffer as communication memory carrying a tag through [`HcclCommMemReg`](https://gitcode.com/cann/hcomm/blob/master/docs/en/api_ref/comm_opdev/control_plane_api/comms_domain_resource_mgmt/HcclCommMemReg.md), so that peers can identify and access it through the channel:

  ```cpp
  constexpr uint64_t SHARD_SIZE = 4096U;               // Size of a single shard.
  const uint64_t COMM_BUF_SIZE = SHARD_SIZE * nranks;  // Accommodate nranks shards.
  constexpr const char* MEMORY_TAG = "shareBuf";

  // Allocate the local communication buffer.
  void* devBuf = nullptr;
  aclrtMalloc(&devBuf, COMM_BUF_SIZE, ACL_MEM_MALLOC_HUGE_FIRST);

  // Initialize the local shard: write to the shard position corresponding to the local rankId.
  std::vector<uint8_t> hostBuffer(static_cast<size_t>(COMM_BUF_SIZE), 0U);
  for (uint64_t i = 0; i < SHARD_SIZE; i++) {
      hostBuffer[rank * SHARD_SIZE + i] = static_cast<uint8_t>(rank);  // Fill the local shard according to the business semantics.
  }
  aclrtMemcpy(devBuf, COMM_BUF_SIZE, hostBuffer.data(), COMM_BUF_SIZE, ACL_MEMCPY_HOST_TO_DEVICE);

  // Register communication memory: the tag is used for peer identification and must be agreed upon by all ranks.
  CommMem registeredMemory = {};
  registeredMemory.type = COMM_MEM_TYPE_DEVICE;
  registeredMemory.addr = devBuf;
  registeredMemory.size = COMM_BUF_SIZE;
  HcclMemHandle memHandle;
  HcclCommMemReg(hcclComm, MEMORY_TAG, &registeredMemory, &memHandle);
  ```

### Obtaining the Peer Link and Creating a Channel

Obtain the communication link to the peer through the topology model that contains the current rank, configure the channel description, and create the channel. For the involved APIs, see [`HcclRankGraphGetLayers`](https://gitcode.com/cann/hcomm/blob/master/docs/en/api_ref/comm_opdev/control_plane_api/topo_info_query/HcclRankGraphGetLayers.md), [`HcclRankGraphGetLinks`](https://gitcode.com/cann/hcomm/blob/master/docs/en/api_ref/comm_opdev/control_plane_api/topo_info_query/HcclRankGraphGetLinks.md), [`HcclChannelDescInit`](https://gitcode.com/cann/hcomm/blob/master/docs/en/api_ref/comm_opdev/control_plane_api/comms_domain_resource_mgmt/HcclChannelDescInit.md), and [`HcclChannelAcquire`](https://gitcode.com/cann/hcomm/blob/master/docs/en/api_ref/comm_opdev/control_plane_api/comms_domain_resource_mgmt/HcclChannelAcquire.md). A channel is a point-to-point resource, so a separate channel must be created for each peer. In the AllGather scenario, the local rank creates one channel with each of the other `nranks - 1` peers:

  ```cpp
  // Query the list of topology layer numbers that contain the current rank and the number of topology layers.
  uint32_t* networkLayers = nullptr;
  uint32_t networkLayerCount = 0;
  HcclRankGraphGetLayers(hcclComm, &networkLayers, &networkLayerCount);

  std::vector<ChannelHandle> channels;  // One channel per peer
  for (uint32_t offset = 1U; offset < nranks; offset++) {
      uint32_t peerRank = (rank + offset) % nranks;

      // Obtain the link to the peer.
      CommLink* links = nullptr;
      uint32_t linkCount = 0;
      HcclRankGraphGetLinks(hcclComm, networkLayers[0], rank, peerRank, &links, &linkCount);

      // Initialize the channel description: remote rank, channel protocol, endpoints on both sides, and local registered memory.
      HcclChannelDesc channelDesc;
      HcclChannelDescInit(&channelDesc, 1U);
      channelDesc.remoteRank = peerRank;
      // RoCE (RDMA over Converged Ethernet, an RDMA protocol over Ethernet) adaptation: change the protocol constant that matches the link here and below to COMM_PROTOCOL_ROCE (the network must provide a RoCE link).
      channelDesc.channelProtocol = COMM_PROTOCOL_UB_CTP;
      channelDesc.memHandles = &memHandle;
      channelDesc.memHandleNum = 1U;
      for (uint32_t i = 0; i < linkCount; i++) {
          if (links[i].linkAttr.linkProtocol == COMM_PROTOCOL_UB_CTP) {
              channelDesc.localEndpoint = links[i].srcEndpointDesc;
              channelDesc.remoteEndpoint = links[i].dstEndpointDesc;
              break;
          }
      }

      // Obtain the channel handle.
      ChannelHandle channel = 0;
      HcclChannelAcquire(hcclComm, COMM_ENGINE_AIV, &channelDesc, 1U, &channel);
      channels.emplace_back(channel);
  }
  ```

### Obtaining the Peer Registered Memory

Query the communication memory registered by the peer through the channel, and match by tag to obtain the remote buffer address (to focus on the call flow, the host-side example omits return value checks and error handling). For details, see [`HcclChannelGetRemoteMems`](https://gitcode.com/cann/hcomm/blob/master/docs/en/api_ref/comm_opdev/control_plane_api/comms_domain_resource_mgmt/HcclChannelGetRemoteMems.md). On the kernel side, the remote write position is calculated based on this address plus an offset:

  ```cpp
  std::vector<uint64_t> remoteBufs(channels.size(), 0U);
  for (uint32_t i = 0; i < channels.size(); i++) {
      uint32_t remoteMemoryCount = 0;
      CommMem* remoteMemories = nullptr;
      char** memoryTags = nullptr;
      HcclChannelGetRemoteMems(hcclComm, channels[i], &remoteMemoryCount, &remoteMemories, &memoryTags);

      for (uint32_t j = 0; j < remoteMemoryCount; j++) {
          if (memoryTags[j] != nullptr && strcmp(memoryTags[j], MEMORY_TAG) == 0) {
              remoteBufs[i] = reinterpret_cast<uint64_t>(remoteMemories[j].addr);
              break;
          }
      }
  }
  ```

### Delivering Handles to the Kernel

Assemble the peer `channel`, the local buffer address `devBuf`, and the peer buffer address `remoteBufs` into a context shared between the host and the kernel (for the structure definition, see [Kernel-Side Communication Execution](#kernel-side-communication-execution); the structure must be defined in a header file shared between the host and the kernel), and then deliver it:

  ```cpp
  void* devContext = nullptr;
  aclrtMalloc(&devContext, sizeof(AllGatherContext), ACL_MEM_MALLOC_HUGE_FIRST);

  AllGatherContext context = {};
  context.localBufferAddr = reinterpret_cast<uint64_t>(devBuf);
  context.rankId = rank;
  context.nranks = nranks;
  context.peerNum = static_cast<uint32_t>(channels.size());
  for (uint32_t i = 0; i < channels.size(); i++) {
      context.channelHandles[i] = channels[i];
      context.remoteBufferAddrs[i] = remoteBufs[i];
  }
  aclrtMemcpy(devContext, sizeof(context), &context, sizeof(context), ACL_MEMCPY_HOST_TO_DEVICE);

  all_gather_kernel<<<1U, nullptr, stream>>>(devContext);
  ```

### Destroying Communication Resources

After the communication task is complete, destroy the communication resources (see [`HcclCommDestroy`](https://gitcode.com/cann/hcomm/blob/master/docs/en/api_ref/comm_mgr_c/HcclCommDestroy.md)). In the sample project, the channel and registered memory are released together with the communicator. For details, see the example [hcomm_urma_write_read_nbi](../../../../examples/aicore/hcomm/01_hcomm_urma_write_read_nbi/README.md):

  ```cpp
  // Destroy the communicator (the channel and registered memory are released together with the communicator).
  HcclCommDestroy(hcclComm);
  // Release the allocated memory.
  aclrtFree(devContext);
  aclrtFree(devBuf);
  // Deinitialize.
  aclrtDestroyStream(stream);
  aclrtResetDevice(static_cast<uint32_t>(rank));
  aclFinalize();
  ```

## Kernel-Side Communication Execution

The kernel entry function is as follows. The channel handle and the local and peer buffer addresses are passed in as input parameters through the `AllGatherContext` context, and the subsequent steps are expanded within this function. The protocol constants on the host side and the kernel side must be consistent (for example, both are `COMM_PROTOCOL_UB_CTP`):

  ```cpp
  #include "hcomm/hcomm.h"

  constexpr uint32_t MAX_PEERS = 16U;  // Upper limit of the number of peers, adjusted based on the networking scale.
  constexpr uint64_t SHARD_SIZE = 4096U;

  struct AllGatherContext {
      uint64_t localBufferAddr;
      uint64_t channelHandles[MAX_PEERS];
      uint64_t remoteBufferAddrs[MAX_PEERS];
      uint32_t rankId;
      uint32_t nranks;
      uint32_t peerNum;  // Number of peers, that is, nranks - 1
  };

  extern "C" __vector__ __global__ __aicore__ void all_gather_kernel(GM_ADDR context)
  {
      // The subsequent kernel-side communication execution tasks are expanded within this function.
  }
  ```

Kernel-side communication APIs are divided into common APIs and batch APIs, both of which are called through the `AscendC::Hcomm` object:

- Common API: directly takes `ChannelHandle` as the input parameter and submits a task on each call. You must first call `Init` to initialize the UB (Unified Buffer) temporary workspace.
- Batch API: takes a batch handle as the input parameter. Multiple tasks are assembled and then submitted together to reduce submission overhead. The UB workspace is bound by `MakeBatchHandle`.

### Performing Preprocessing

Allocate a UB temporary workspace (no less than 512 bytes), create an `AscendC::Hcomm` object and call `Init` to initialize the workspace, and then parse the channel and address information in the context:

  ```cpp
  // Initialize the UB temporary workspace size: it must be no less than 512 bytes.
  constexpr uint32_t HCOMM_WORKSPACE_SIZE = 512U;

  // Prepare the UB temporary workspace. alignas(32) ensures that the start address is 32-byte aligned.
  alignas(32) __ubuf__ uint8_t hcommLocal[HCOMM_WORKSPACE_SIZE];

  // Create an Hcomm object and initialize the temporary workspace used by the common API.
  // RoCE adaptation: change the template protocol to AscendC::COMM_PROTOCOL_ROCE, consistent with the host-side channel protocol.
  AscendC::Hcomm<AscendC::COMM_PROTOCOL_UB_CTP> hcomm;
  int32_t ret = hcomm.Init(hcommLocal, HCOMM_WORKSPACE_SIZE);

  // Parse the context: local buffer address and rank information.
  __gm__ AllGatherContext* ctx = reinterpret_cast<__gm__ AllGatherContext*>(context);
  __gm__ uint8_t* localBuf = reinterpret_cast<__gm__ uint8_t*>(ctx->localBufferAddr);
  uint32_t rankId = ctx->rankId;
  ```

### Submitting Communication Tasks

AllGather: Traverse all peer channels and write the local shard (located at the `rankId * SHARD_SIZE` offset) to the same offset in each peer buffer. After the communication completes, the buffer of each rank holds the shard of rank k at the `k * SHARD_SIZE` offset, which is the AllGather result:

  ```cpp
  for (uint32_t i = 0U; i < ctx->peerNum; i++) {
      AscendC::ChannelHandle channel = ctx->channelHandles[i];
      __gm__ uint8_t* remoteBuf = reinterpret_cast<__gm__ uint8_t*>(ctx->remoteBufferAddrs[i]);
      __gm__ uint8_t* remoteDst = remoteBuf + static_cast<uint64_t>(rankId) * SHARD_SIZE;
      __gm__ uint8_t* localSrc = localBuf + static_cast<uint64_t>(rankId) * SHARD_SIZE;
      ret = hcomm.WriteNbi(channel, remoteDst, localSrc, SHARD_SIZE);
  }
  ```

When there are many communication tasks, you can set `commit = false` to defer submission and reduce submission overhead. For details, see [Deferred Submission and Batch Optimization](#deferred-submission-and-batch-optimization).

### Waiting for Completion

Call `Drain` channel by channel to block and wait for all tasks on that channel to complete:

  ```cpp
  for (uint32_t i = 0U; i < ctx->peerNum; i++) {
      ret = hcomm.Drain(ctx->channelHandles[i]);
  }
  ```

`Drain` only guarantees that the tasks submitted on the local channel are complete. AllGather requires that the result be complete only after all data exchange is finished: on the host side, after `aclrtSynchronizeStream`, you need to confirm through inter-rank synchronization (such as a TCP control channel barrier) that the kernels of all ranks have completed before verifying or using the AllGather result. If the device side needs to sense data arrival, you can use `WriteWithNotifyNbi` and `AtomicFAA`. For details, see [Notification and Atomic Operations](#notification-and-atomic-operations).

## Notification and Atomic Operations

`WriteWithNotifyNbi` writes a notification value to the peer notify address after writing data, which can be used by the peer to detect data arrival. `AtomicFAA`/`AtomicCAS` perform atomic accumulation and compare-and-swap on remote registered memory. The preceding APIs support only the `COMM_PROTOCOL_UB_CTP` protocol:

  ```cpp
  // channel is the local channel handle, remoteDst/localSrc are the remote destination and local source GM addresses, and len is the write length.
  // notifyAddr, remoteCounter, and remoteValue are addresses in the peer registered memory, and fetchAddr is the local address for retrieving the old value.
  // notifyVal/addVal/compareVal/swapVal are the notification value and atomic operands agreed upon by the service.
  // Write data and write notifyVal to the peer notifyAddr.
  ret = hcomm.WriteWithNotifyNbi(channel, remoteDst, localSrc, len, notifyAddr, notifyVal);
  // Remote atomic accumulation.
  ret = hcomm.AtomicFAA<uint64_t>(channel, remoteCounter, fetchAddr, addVal);
  // Remote atomic compare-and-swap.
  ret = hcomm.AtomicCAS<uint64_t>(channel, remoteValue, fetchAddr, compareVal, swapVal);
  ```

The preceding APIs can be used to implement the local synchronization and remote synchronization described in the synchronization mechanism section of [Execution Model](../programming_model/execution_model.md):

### Local Synchronization

`Drain` implements local synchronization: it blocks until all communication tasks submitted on the specified channel are complete (by polling the completion queue internally). Taking a remote read as an example, after submitting a read task, you must complete local synchronization before accessing the read result; otherwise, you may read data that has not been fully updated:

  ```cpp
  // Prerequisites: channel is the local channel handle, remoteSrc is the source GM address in the peer's registered memory, localDst is the local destination GM address, and len is the read length.
  ret = hcomm.ReadNbi(channel, localDst, remoteSrc, len);  // One-sided read: read the peer's src data into the local dst.
  ret = hcomm.Drain(channel);                              // Local synchronization: wait for the submitted tasks on this channel to complete.
  // Local synchronization is complete, and the data in localDst can be safely accessed.
  ```

### Remote Synchronization

`Drain` only confirms that the local tasks are complete; it cannot detect whether the data sent by the peer to the local side is ready. When the device side needs to detect data arrival, use point-to-point remote synchronization: the peer sends a synchronization signal after writing data, and the local side polls the signal and accesses the data only after confirmation.

The write side carries a synchronization signal while writing data: `WriteWithNotifyNbi` completes both the data write and the notify write in a single call, with `notifyVal` incremented per synchronization round. For a counter-based signal, you can instead call `WriteNbi` to write data and then append `AtomicFAA` to atomically increment the peer counter (see the call form above). After task submission, call `Drain` to wait for completion:

  ```cpp
  // notifyAddr is the notify address in the peer (read side) registered memory
  ret = hcomm.WriteWithNotifyNbi(channel, remoteDst, localSrc, len, notifyAddr, notifyVal);
  ret = hcomm.Drain(channel);
  ```

The read side polls its local notify address until it reaches the expected value, confirming that the peer data has been fully written:

  ```cpp
  // notifyAddr is the notify address in the local registered memory (written by the write side), which must be 32-byte aligned.
  // expectedNotifyVal is the expected value the local side waits for, incremented per synchronization round.
  AscendC::GlobalTensor<uint64_t> notifyGm;
  notifyGm.SetGlobalBuffer(reinterpret_cast<__gm__ uint64_t*>(notifyAddr));

  // The DataCopy transfer amount is 32-byte aligned, reading four uint64_t at a time.
  constexpr uint32_t SYNC_COUNT = 4U;
  // Prepare the UB workspace; alignas(32) ensures the start address is 32-byte aligned.
  alignas(32) __ubuf__ uint64_t syncWorkspace[SYNC_COUNT];
  // Construct the synchronous read LocalTensor from the start address of the UB workspace.
  AscendC::LocalTensor<uint64_t> syncLocal(
      AscendC::TPosition::VECIN,
      static_cast<uint32_t>(reinterpret_cast<uintptr_t>(syncWorkspace)), SYNC_COUNT);
  uint64_t observed = 0U;
  do {
      AscendC::DataCopy(syncLocal, notifyGm, SYNC_COUNT);
      // MTE2 -> V: After the data copy is complete, read the notify value from UB (see the SetFlag/WaitFlag synchronization mode in example 03, and select the event type based on the read pipeline).
      AscendC::SetFlag<AscendC::HardEvent::MTE2_V>(EVENT_ID0);
      AscendC::WaitFlag<AscendC::HardEvent::MTE2_V>(EVENT_ID0);
      observed = syncLocal.GetValue(0);
      // V -> MTE2: Only after the previous read is complete can the next DataCopy overwrite the same UB workspace (to avoid WAR hazards, see the reverse synchronization mode in example 03).
      AscendC::SetFlag<AscendC::HardEvent::V_MTE2>(EVENT_ID0);
      AscendC::WaitFlag<AscendC::HardEvent::V_MTE2>(EVENT_ID0);
  } while (observed < expectedNotifyVal);
  // Point-to-point synchronization is complete, and the data written by the peer can be safely accessed.
  ```

Barrier synchronization is collective-level remote synchronization, and Hcomm does not provide a corresponding API: the barriers before and after collective semantics such as AllGather are completed by synchronization between ranks on the host side (see [Waiting for Completion](#waiting-for-completion)); when a barrier is truly required on the device side, you can accumulate a shared counter in the registered memory of the agreed rank based on `AtomicFAA`, and then poll the counter value through point-to-point synchronization until all ranks have arrived. Barrier synchronization introduces global waiting and should be avoided; when remote synchronization is required, prefer point-to-point synchronization.

## Deferred Submission and Batch Optimization

### Deferred Submission

By default, a common API submits immediately on each call. Setting `commit = false` when submitting a task defers submission until an explicit `Commit` call, reducing submission overhead:

  ```cpp
  // Prerequisites: channel is the local channel handle, dst is the destination GM address in the remote registered memory, src is the local source GM address, and len is the write length.
  // Deferred submission: only add the task without submitting it.
  ret = hcomm.WriteNbi<false>(channel, dst, src, len);
  // Explicitly submit all accumulated tasks.
  ret = hcomm.Commit(channel);
  // Wait for all tasks on this channel to complete.
  ret = hcomm.Drain(channel);
  ```

When the `commit` template parameter is set to `false`, the total number of slots occupied by accumulated deferred-submission tasks must not exceed the task submission capacity of the channel (the send queue depth `sqDepth`). Submit the accumulated tasks through `Commit` or automatic commit before the SQ is exhausted; otherwise, subsequent task submission fails due to SQ overflow.

### Batch Submission

When multiple tasks need to be assembled and submitted together, use the batch API. The batch API assembles multiple tasks through a batch handle and submits them together, without calling `Init`; its UB workspace is bound by `MakeBatchHandle`. Based on the number of channels, it is divided into two forms: single-channel batch and multi-channel batch. Under the `COMM_PROTOCOL_UB_CTP` protocol, read, write, and write-notify tasks can be mixed in the same batch; under the `COMM_PROTOCOL_ROCE` protocol, only batch read and write tasks are supported.

#### Single-Channel Batch

When multiple tasks need to be submitted to the same channel, assemble the tasks through a batch handle and submit them together:

  ```cpp
  // Prerequisites: channel is the local channel handle, and remoteAddr is used to select the remote registered memory.
  // remoteWriteDst/localWriteSrc/writeLen are the destination/source GM addresses and length of the write task.
  // localReadDst/remoteReadSrc/readLen are the destination/source GM addresses and length of the read task, all prepared by the caller according to the service.
  // Batch workspace length: at least 64 bytes, divided into 64-byte task slots.
  constexpr uint32_t batchBufferLen = 128U;
  // Declare the batch UB workspace; alignas(32) ensures the start address is 32-byte aligned.
  alignas(32) __ubuf__ uint8_t batchWorkspace[batchBufferLen];
  // Construct the batch workspace LocalTensor from the start address of the UB workspace.
  AscendC::LocalTensor<uint8_t> batchBuffer(
      AscendC::TPosition::VECOUT,
      static_cast<uint32_t>(reinterpret_cast<uintptr_t>(batchWorkspace)), batchBufferLen);
  // Create a batch handle and bind the batch workspace; remoteAddr is used to select the remote registered memory.
  auto batchHandle = hcomm.MakeBatchHandle(channel, batchBuffer, batchBufferLen, remoteAddr);

  // Add read, write, and write-notify tasks; they can be mixed within the same batch.
  ret = hcomm.WriteNbi(batchHandle, remoteWriteDst, localWriteSrc, writeLen);
  ret = hcomm.ReadNbi(batchHandle, localReadDst, remoteReadSrc, readLen);
  // Submit the current batch.
  ret = hcomm.BatchCommit(batchHandle);
  // Wait for the tasks submitted by this batch handle to complete.
  ret = hcomm.Drain(batchHandle);
  ```

`remoteAddr` specifies the remote registered memory accessed by the tasks in this batch: under the `COMM_PROTOCOL_UB_CTP` protocol, this parameter does not take effect and the first remote registered buffer is used by default; under the `COMM_PROTOCOL_ROCE` protocol, it must be explicitly passed in (for the multi-SGE scenario, see [Multi-SGE Batch Read/Write](#multi-sge-batch-readwrite)). After `BatchCommit` is submitted successfully, you can reuse the batch handle and workspace to continue adding and submitting the next batch of tasks.

For the complete flow, see the example [hcomm_roce_batch_write_read](../../../../examples/aicore/hcomm/08_hcomm_roce_batch_write_read/README.md) (COMM_PROTOCOL_ROCE protocol).

#### Multi-Channel Batch

When tasks need to be submitted to multiple peers in batch, the host side creates a multi-channel handle through `MakeMultiChannelHandle`. When resources are managed using an HCCL communicator, the communicator overload is used, and the created resources are automatically released when the communicator is destroyed:

  ```cpp
  #include "hcomm/hcomm_host.h"

  // channelDescs/channelNum: array of channel descriptors grouped by local endpoint and its count, prepared by the caller.
  // sharedQueueTag: tag of the shared submission queue across multiple channels, constructed by the caller.
  MultiChannelHandle multiChannel = 0U;
  HcclResult ret = MakeMultiChannelHandle(
      hcclComm, sharedQueueTag, channelDescs, channelNum, &multiChannel);
  ```

When the HCCL communicator is not used, pass the Hcomm endpoint and `HcommChannelDesc` to call another overload. After the kernel finishes execution and synchronization, destroy the multi-channel handle first, and then destroy the endpoint:

  ```cpp
  // endpointHandle: Hcomm endpoint handle, obtained from the endpoint creation API.
  HcommResult ret = MakeMultiChannelHandle(
      endpointHandle, channelDescs, channelNum, &multiChannel);

  // After the kernel finishes execution and synchronization, destroy the handle and the endpoint.
  ret = DestroyMultiChannelHandle(multiChannel);
  // HcommEndpointDestroy: external API for destroying the Hcomm endpoint, provided by the hcomm external component (paired with the endpoint overload of MakeMultiChannelHandle).
  ret = HcommEndpointDestroy(endpointHandle);
  ```

On the AI Core side, use `GetHandleRef` to select the logical channel (corresponding to the `channelDescs` array subscript) and the remote registered memory, and then add, submit, and wait for tasks through the multi-channel batch handle:

  ```cpp
  // remoteBuffers: remote registered memory addresses corresponding to each logical channel; localBuffer/dataLen: local data address and length.
  auto multiBatchHandle = hcomm.MakeBatchHandle(
      static_cast<AscendC::MultiChannelHandle>(multiChannel), batchBuffer, batchBufferLen);

  for (uint32_t channelIndex = 0U; channelIndex < channelNum; ++channelIndex) {
      auto& peerBatchHandle = hcomm.GetHandleRef(multiBatchHandle, channelIndex, remoteBuffers[channelIndex]);
      ret = hcomm.WriteNbi(peerBatchHandle, remoteBuffers[channelIndex], localBuffer, dataLen);
  }
  ret = hcomm.BatchCommit(multiBatchHandle);
  ret = hcomm.Drain(multiBatchHandle);
  ```

When switching the logical channel or remote registered memory, call `GetHandleRef` again. Repeated calls on the same multi-channel batch handle return a reference to the same inner **BatchHandle**, and its logical channel and remote registered memory selection are updated with the most recent call.

For the complete flow, see the example [hcomm_urma_batch_write](../../../../examples/aicore/hcomm/02_hcomm_urma_batch_write/README.md).

## Multi-SGE Batch Read/Write

Multi-SGE (Scatter Gather Element) batch read/write is supported: a single `WriteNbi`/`ReadNbi` describes multiple local discrete data segments through a `BufDesc` array and performs aggregated read/write on a contiguous memory range on the remote end, which is suitable for scenarios where source data is stored in discrete blocks.

Multi-SGE is supported by the `COMM_PROTOCOL_UB_CTP` and `COMM_PROTOCOL_ROCE` protocols, and is implemented only through the batch API: the common API `WriteNbi`/`ReadNbi` does not support the `BufDesc` input parameter, so multi-SGE tasks must be submitted through a batch handle created by `MakeBatchHandle`. The number of data segments in `srcDescs`/`dstDescs` is 1-13 under the `COMM_PROTOCOL_UB_CTP` protocol and 1-24 under the `COMM_PROTOCOL_ROCE` protocol. Under the `COMM_PROTOCOL_ROCE` protocol, when creating a batch handle, both the remote and local registered memory must be bound: `localAddr` must be an address in the local registered memory and is used to bind the local memory protection information; the address of each data segment in `srcDescs`/`dstDescs` must be within the bound registered memory range, and the `len` of each data segment and the accumulated total length must both be less than 2 GB (2 * 1024 * 1024 * 1024 bytes). Under the `COMM_PROTOCOL_UB_CTP` protocol, `localAddr` does not take effect, and `remoteAddr` always uses the first remote registered buffer (see [Single-Channel Batch](#single-channel-batch)). The validity of the address and length of each data segment is guaranteed by the caller; the addresses of the data segments are not verified when the handle is created, and violations are exposed during task submission or execution.

  ```cpp
  // Create a batch handle: bind both the remote registered memory and the local registered memory.
  auto batchHandle = hcomm.MakeBatchHandle(channel, batchBuffer, batchBufferLen, remoteAddr, localAddr);

  // Single write: write SGE_NUM local discrete data segments to the remote contiguous range remoteDst (SGE_NUM/SEGMENT_STRIDE/SEGMENT_SIZE are the segment count, stride, and segment length agreed upon by the service, and remoteDst must be within the registered memory where remoteAddr resides).
  AscendC::BufDesc srcDescs[SGE_NUM];
  for (uint32_t i = 0; i < SGE_NUM; i++) {
      srcDescs[i].addr = localAddr + i * SEGMENT_STRIDE;  // Local discrete segment address.
      srcDescs[i].len = SEGMENT_SIZE;
  }
  ret = hcomm.WriteNbi(batchHandle, remoteDst, srcDescs, SGE_NUM);

  // Single read: read back SGE_NUM local discrete data segments from the remote contiguous range remoteSrc (remoteSrc must be within the registered memory where remoteAddr resides).
  AscendC::BufDesc dstDescs[SGE_NUM];
  // Fill dstDescs in the same way.
  ret = hcomm.ReadNbi(batchHandle, dstDescs, SGE_NUM, remoteSrc);

  // Submit and wait for this batch of tasks to complete.
  ret = hcomm.BatchCommit(batchHandle);
  ret = hcomm.Drain(batchHandle);
  ```

For the complete flow, see the example [hcomm_roce_multi_sge](../../../../examples/aicore/hcomm/09_hcomm_roce_multi_sge/README.md).

## Sharing a Channel Across Multiple AI Cores

When multiple AIVs (AI Vector) share the same `COMM_PROTOCOL_UB_CTP` channel, use [Lock](../../api/aicore/hcomm/Lock.md) and [Unlock](../../api/aicore/hcomm/Unlock.md) to protect accesses that update the channel state. Each AI Core can use an independent Hcomm object and UB temporary workspace, but passes the same `ChannelHandle`. The lock cannot be reentered. After each successful `Lock`, `Unlock` must be called by the same AI Core, and the lock must also be released on error exit paths. The APIs only synchronize AI Cores on the same device that share the same channel:

  ```cpp
  int32_t lockRet = hcomm.Lock(channel);
  if (lockRet == 0) {
      int32_t opRet = hcomm.WriteNbi(channel, dst, src, len);
      // Even if the communication API returns a failure, release the lock that has been successfully acquired.
      int32_t unlockRet = hcomm.Unlock(channel);
      // Handle opRet and unlockRet separately.
  }
  ```

## Precautions

- For common APIs, call `Init` first to provide a UB temporary workspace of at least 512 bytes. When using `__ubuf__ uint8_t*`, the start address must be 32-byte aligned. When using `LocalTensor`, ensure that the tensor capacity meets the workspace requirement.
- The host-side channel protocol (`HcclChannelDesc.channelProtocol`) must be consistent with the kernel-side `Hcomm` template protocol.
- A channel is a point-to-point resource. Each peer requires a separate `HcclChannelAcquire`. In a ring multi-peer scenario, it is recommended to stagger the link establishment order by rank parity to avoid circular waiting. When `nranks == 2`, the previous and next peers are the same, so the same channel can be reused.
- Data length of a single `WriteNbi`/`ReadNbi`: under the `COMM_PROTOCOL_UB_CTP` protocol, it must not exceed 256 MB; under the `COMM_PROTOCOL_ROCE` protocol, it must be less than 2 GB (2 * 1024 * 1024 * 1024 bytes).
- `WriteWithNotifyNbi`, `WriteValueNbi`, `WriteReduceNbi`, `AtomicFAA`, and `AtomicCAS` support only the `COMM_PROTOCOL_UB_CTP` protocol.
- The data type of the atomic operation supports only `int32_t`, `uint32_t`, `int64_t`, and `uint64_t`.
