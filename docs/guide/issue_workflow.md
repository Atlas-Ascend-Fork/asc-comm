# Issue 提交流程

## 适用场景

提交代码前应先查询已有 Issue，确认问题、需求或文档反馈是否已被跟踪。简单修复可以创建或关联 Issue 后直接提交 PR；新增接口、协议路径、配置参数、行为变更或较大集成样例，应先提交需求类 Issue 完成方案讨论。

本仓 Issue 模板放在 `.gitcode/ISSUE_TEMPLATE/`，类型和字段参考 devkit。

## Issue 类型

| 类型 | 适用场景 | 需要说明 |
| --- | --- | --- |
| `Bug-Report\|缺陷反馈` | Hcomm API 行为异常、UT 失败、构建脚本错误、文档示例无法按说明执行。 | 问题描述、环境信息、复现步骤、预期结果、实际日志。 |
| `Requirement\|需求建议` | 新接口、新协议支持、兼容性增强、端到端样例、测试能力扩展。 | 背景、来源、业务价值、影响范围、初步设计。 |
| `Documentation\|文档反馈` | API 说明错误、使用流程缺失、样例说明不清、依赖说明不完整。 | 文档链接或路径、问题片段、建议修改方向。 |
| `Question\|问题咨询` | 使用方式、接口约束、外部 hcomm/devkit 集成边界等问题。 | 问题描述、已尝试的命令或参考资料。 |

## 填写建议

缺陷类 Issue 建议包含：

- 分支、提交号、CANN 版本、NPU 型号、操作系统和编译器版本。
- 执行命令，例如 `bash build.sh -t` 或手动 CMake 命令。
- 失败日志、GTest 过滤项、返回码或截图。
- 若涉及 Hcomm 协议，说明 `COMM_PROTOCOL_ROCE` 或 `COMM_PROTOCOL_UBC_CTP`。

需求类 Issue 建议包含：

- 目标场景和用户收益。
- 是否影响公开 API、ABI、文档、样例或三方依赖清单。
- 与 devkit/hcomm/CANN 外部能力的依赖关系。
- 初步方案、替代方案和兼容性风险。

文档类 Issue 建议包含：

- 文档路径，例如 `docs/api/aicore/hcomm/Hcomm.md`。
- 有问题的章节、表格、示例或链接。
- 期望补充的约束、命令、样例或版本说明。

## 认领与处理

参考 CANN 社区流程，创建或找到目标 Issue 后，可在评论区输入 `/assign` 或 `/assign @yourself` 认领。处理过程中如果发现范围扩大，应在 Issue 中补充新的影响面和方案，再继续提交 PR。

## 与 PR 的关系

所有 PR 都应关联 Issue，并在 PR 描述中写明：

- 关联的 Issue 编号。
- 修改背景、目的和方案摘要。
- 本地验证命令和结果。
- 对 CANN 版本、NPU 架构、hcomm/devkit 外部依赖的假设。
- API、文档、样例或测试行为的变化。

复杂需求应先在 Issue 中达成方向一致，再提交实现 PR。若不确定修改是否属于简单修复，也建议先提交 Issue 讨论。
