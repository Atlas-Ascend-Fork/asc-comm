# 内存模型

通信会涉及多种内存资源。下表汇总了通信编程中常见内存的物理位置及其跨端访问能力。

**表1** 内存资源及其跨端访问能力

| 内存资源 | 物理位置 | 本端参与跨端访问 | 对端发起访问 |
| --- | --- | --- | --- |
| Global Memory（GM） | Device全局内存 | 远端写时可作为本端源，远端读时可作为本端目的；| 通信内存向对端开放后，可作为远端读的源或远端写的目的。 |
| Unified Buffer | AI Core片内 | 不作为远端读写的本端操作数。 | 不支持作为远端读写的操作数。 |
| AI Core寄存器 | AI Core片内 | 不作为远端读写的本端操作数。 | 不支持作为远端读写的操作数。 |
| CCU Buffer | CCU片内 | 远端写时可作为本端源，远端读时可作为本端目的。 | 不支持作为远端读写的操作数。 |
| CCU寄存器 | CCU片内 | 可通过Channel向对端写入地址、`Token`、数据长度等通信参数，或发送同步通知。 | 可通过Channel接收对端写入的通信参数或同步通知。 |

- GM按主要用途可以分为计算内存和通信内存。计算内存保存计算的输入、输出和中间结果；通信内存承载跨端传输的源数据和目的数据。远端写请求通过访问校验后，写入目标GM地址对应的L2 Cache，L2 Cache与GM之间的数据一致性由硬件维护。
- Unified Buffer位于AI Core内部。在通算融合过程中，计算数据通过Unified Buffer在计算单元与GM之间搬运；计算结果需要参与通信时，先从Unified Buffer搬到GM中的通信内存，通信数据到达本端GM后也可以搬入Unified Buffer继续计算。
- CCU Buffer是CCU内部的片上存储资源，用于暂存、中转和归约通信数据。
- CCU寄存器位于CCU内部，用于保存访问地址、`Token`、数据长度等通信参数和同步状态。

![内存层级和通信能力](./figures/memory_model.png "内存层级和通信能力")

[图1](#fig-memory-hierarchy-communication-capability)从上到下展示GM、L2 Cache和执行引擎片内资源之间的层级关系，本端和远端分别拥有各自的GM、L2 Cache和片内资源。

在这些资源中，通信内存和CCU片上资源能够直接参与跨端通信：通信内存可以作为远端读的源范围或远端写的目的范围；CCU的CCU Buffer可以在本端CCU发起的传输中与对端GM搬运数据，CCU寄存器可以通过Channel与对端传递通信参数和同步通知。Unified Buffer和AI Core寄存器主要承担本端缓存、数据暂存和计算。基于这种能力差异，下文重点说明通信内存的组织与访问机制，以及CCU片上资源的通信方式。

## 通信内存

通信内存在物理上位于GM，是经过控制面准备、能够作为通信操作数并可向对端开放的内存范围。通信内存承载跨端传输的源数据和目的数据。

通信开始前，控制面记录通信内存的有效范围，并为其建立通信关系和访问授权；数据面依据这些资源执行通信操作。通信内存从准备到组织的过程如[图2](#fig-communication-memory-flow)所示。

**图2** 通信内存的准备与组织<a id="fig-communication-memory-flow"></a>

![通信内存的准备与组织](./figures/communication_memory_flow.png "通信内存的准备与组织")

下文依次说明通信内存如何建立远端可见性、访问凭据如何保护内存范围，以及程序如何组织通信内存并描述目标成员和内存位置。

### 远端可见性

一段GM内存通过以下步骤建立远端可见性：

1. 控制面记录内存的起始地址、大小和有效范围。
2. 控制面按照通信协议注册该内存，并为有效范围建立访问凭据。
3. 建立Channel，确定该Channel可以使用的通信内存。
4. 向对端交换内存描述和远端访问所需的凭据。

完成上述准备后，对端获得目标内存的地址范围和访问授权，并可以通过已建立的Channel访问该段内存。

具备远端可见性后，通过以下信息发起远端访问：

- Channel用于确定通信对端和已经建立的通信关系。
- 远端地址和访问长度用于描述对端内存中的目标范围。
- 访问凭据用于表明本次操作获得了目标内存范围的访问授权。

具体的通信内存注册、Channel创建和远端内存获取流程，可参考[Hcomm AIV直驱URMA样例](../../../examples/aicore/hcomm/01_hcomm_write_read_nbi/README.md)。

### 访问凭据

访问凭据由内存注册过程为注册范围建立，用于表达通信任务对该范围的访问授权。建立Channel时，目标内存的地址范围及远端访问所需的凭据会交换给对端；执行通信任务时，通信硬件依据凭据校验对本地或远端注册内存的访问。不同通信协议采用的凭据机制如下。

**表2** 不同通信协议的访问凭据机制

| 协议类型 | 访问凭据 | 校验机制 |
| --- | --- | --- |
| RoCE | `lkey`、`rkey` | `lkey`用于校验通信引擎对本地操作数的访问，`rkey`用于校验对目标端注册内存的远端访问。 |
| UB类协议 | `tokenId`、`tokenValue` | `tokenId`用于定位目标内存对应的保护信息，`tokenValue`用于校验访问权限；二者需要与目标地址范围匹配。 |

#### RoCE访问过程

以成员0将本端内存A写入成员1的内存B为例，访问过程如[图3](#fig-roce-remote-write)所示：

1. 成员0注册内存A，获得用于本地访问的`lkey_A`。
2. 成员1注册内存B，获得用于授权远端访问的`rkey_B`。
3. 建立Channel时，成员1将内存B的地址范围和`rkey_B`交换给成员0。
4. 成员0发起写操作时，通信任务携带内存A的本地地址和`lkey_A`，以及内存B的远端地址和`rkey_B`。
5. 发起端通信硬件使用`lkey_A`校验对内存A的读取，目标端通信硬件使用`rkey_B`校验对内存B的写入。两项校验通过后，数据才能写入内存B。

**图3** RoCE远端写访问过程<a id="fig-roce-remote-write"></a>

![RoCE远端写访问过程](./figures/roce_remote_write.png "RoCE远端写访问过程")

一次RoCE远端写同时使用发起端本地源内存的`lkey`和目标端目的内存的`rkey`。二者分别保护本地操作数和远端操作数，并与各自的注册内存范围匹配。

#### UB类协议访问过程

仍以成员0将本端内存A写入成员1的内存B为例，访问过程如[图4](#fig-ub-remote-write)所示：

1. 成员1注册内存B，为该内存范围建立`tokenId_B`和`tokenValue_B`。
2. 建立Channel时，成员1将内存B的地址范围、`tokenId_B`和`tokenValue_B`交换给成员0。
3. 成员0发起写操作时，通信任务携带内存B的远端地址、访问长度、`tokenId_B`和`tokenValue_B`。
4. 目标端通信硬件根据`tokenId_B`定位内存B对应的保护信息，使用`tokenValue_B`校验访问权限，并检查远端地址和访问长度是否落在该保护信息对应的注册范围内。
5. `Token`和目标内存范围均匹配后，数据才能写入内存B。

**图4** UB类协议远端写访问过程<a id="fig-ub-remote-write"></a>

![UB类协议远端写访问过程](./figures/ub_remote_write.png "UB类协议远端写访问过程")

完成内存注册、Channel建立和访问凭据交换后，通信双方已经具备访问对端通信内存的基础条件。上层编程模型还需要向用户提供一种方式，用于指定目标成员及其内存位置。

### 通信内存的组织

根据通信内存向用户呈现的组织方式，可以分为非对称内存和对称内存。两种组织方式都建立在Channel、实际GM地址范围和访问凭据之上，区别在于用户如何指定目标成员和内存位置。

两种组织方式的差异如下表所示。

**表3** 通信内存组织方式对比

| 组织方式 | 用户看到的内存组织 | 每次操作提供的信息 | 底层处理方式 |
| --- | --- | --- | --- |
| 非对称内存 | 各成员分别管理通信内存 | Channel、本地地址和远端地址 | 根据Channel确定目标成员；本地地址指定本端数据的来源或去向，远端地址定位对端内存。 |
| 对称内存 | 各成员的对应内存组成逻辑窗口 | 目标成员、窗口和窗口内偏移 | 选择目标成员对应的Channel，将偏移解析为实际地址并匹配访问凭据。 |

#### 非对称内存

非对称内存是指各成员的通信内存彼此独立，不同成员的内存大小、布局和实际地址可以不同，不要求形成统一的逻辑布局。采用非对称内存时，各通信成员分别申请和管理自己的通信内存。

发起通信时，用户通过Channel指定目标成员，并分别提供本地地址和远端地址。写操作从本地地址读取数据并写入远端地址，读操作从远端地址读取数据并写入本地地址。底层根据Channel确定通信对端，根据远端地址和访问长度定位对端注册内存，并匹配本次访问所需的凭据。

```text
Channel + 本地地址 + 远端地址 + 访问长度
        -> 确定目标成员
        -> 本地地址确定本端数据范围
        -> 远端地址和访问长度定位对端注册内存
        -> 匹配访问凭据并传输数据
```

Hcomm原语编程和基于CCU原始指令直接编程均采用非对称内存组织，以下示例场景用于进一步说明非对称内存。

假设成员0要把本端源GM内存A中偏移64字节开始的256字节数据，写入成员1的通信内存B中偏移128字节的位置。A和B由两个成员分别准备，其起始地址和内存布局不需要相同。建立Channel时，成员1的内存B及其远端访问凭据已经交换给成员0。Hcomm伪码实现：

```cpp
// localMemA：本端源GM内存A的起始地址
// remoteMemB：成员1的通信内存B的远端起始地址
auto localAddr = localMemA + 64;
auto remoteAddr = remoteMemB + 128;

hcomm.WriteNbi(
    channelToMember1, // 通往成员1的Channel
    remoteAddr,       // 远端目的位置
    localAddr,        // 本地源位置
    256);             // 传输长度，单位为字节
```

调用中的`channelToMember1`、`localAddr`和`remoteAddr`分别确定目标成员、本地源位置和远端目的位置。Hcomm原语内随后完成以下处理：

1. 根据Channel确定目标成员1。
2. 根据`localAddr`和传输长度确定本地源范围，根据`remoteAddr`和传输长度确定远端目的范围。

根据Channel采用的通信协议，地址范围和访问凭据的匹配方式如下：

- RoCE路径：本地`src`和远端`dst`分别匹配本地、远端注册内存，并取得本地`lkey`和远端`rkey`。
- UB类协议路径：远端`dst`匹配Channel中注册的远端Buffer及其`Token`；本地`src`仅需满足`WriteNbi`接口的GM地址和长度约束，不查询本地注册内存，也不匹配本地访问凭据。

完成相应的范围和凭据匹配后，发起数据传输。本次写操作中，本地地址始终表示数据源，远端地址始终表示数据目的；RoCE还需要为本地源匹配`lkey`，UB类协议只为远端目的匹配`Token`。

#### 对称内存

采用对称内存时，各通信成员分别提供一段本端通信内存，这些对应内存被共同组织为一个逻辑窗口。用户通过目标成员、窗口和窗口内偏移描述访问位置，底层据此解析Channel和远端实际地址。

```text
目标成员 + 逻辑窗口 + 窗口内偏移 + 访问长度
        -> 选择该成员对应的Channel和窗口内存
        -> 将窗口内偏移解析为实际GM地址
        -> 匹配访问凭据并传输数据
```

对称性体现在各成员使用一致的逻辑组织和偏移规则，各成员对应内存的实际地址可以不同。窗口中的每个成员对应一段实际GM，底层选择目标成员对应的Channel，将偏移换算为实际地址，并使用与该内存范围匹配的访问凭据。

基于Ain接口编程实现通信是采用对称内存的示例，以下示例场景用于进一步说明对称内存。

假设一个逻辑窗口由成员0、成员1和成员2各自提供的一段通信内存组成，这三段内存的实际起始地址可以不同。成员0要把本地窗口中偏移64字节开始的256字节数据写入成员2的窗口偏移128字节处。Ain伪码实现：

```cpp
ain.Put(
    communicationGroup, // 当前通信组
    2,                  // 目标成员
    window, 128,        // 目的窗口及窗口内偏移
    window, 64,         // 源窗口及窗口内偏移
    256,                // 传输长度，单位为字节
    /* 其余参数省略 */);
```

与Hcomm原语编程示例相比，这次调用没有直接给出通往成员2的Channel和远端GM地址，而是通过目标成员、窗口和窗口内偏移表达访问位置。Ain随后完成以下处理：

1. 根据目标成员2选择通往该成员的Channel。
2. 使用窗口中记录的成员0实际内存起始地址加源偏移，得到本地GM地址。
3. 使用窗口中记录的成员2实际内存起始地址加目的偏移，得到远端GM地址。
4. 通过底层Hcomm接口匹配相应的访问凭据并发起写操作。

用户面对的是统一的逻辑窗口、目标成员和窗口内偏移。底层Channel、实际GM地址和访问凭据由Ain及其复用的Hcomm接口完成解析和匹配。

## CCU片上内存模型

通信内存位于GM，用于承载跨端传输的源数据和目的数据，并通过内存注册、Channel和访问凭据建立远端访问条件。CCU执行通信任务时，使用片上的CCU Buffer暂存、中转和归约数据，并使用寄存器保存搬运参数和同步状态。这两类片上资源共同配合GM中的通信内存完成数据搬运和处理。

### CCU Buffer

CCU Buffer是CCU内部的片上缓存，支持以下数据搬运路径：

- 本地搬运：本端GM与本端CCU Buffer之间可以双向搬运数据。
- 读取远端：本端CCU从对端GM读取通信数据，并写入本端CCU Buffer。
- 写入远端：本端CCU从本端CCU Buffer读取数据，并写入对端GM。

跨端搬运由持有CCU Buffer的本端CCU发起，远端操作数位于对端GM。对端发起远端写时，目的范围位于本端GM中的通信内存。

归约时，CCU可以将不同来源的数据暂存在CCU Buffer中，在片上按序完成归约，再将结果写入本端或对端GM。中间数据保留在CCU片上，可以减少集合通信过程中对GM的重复读写。

### CCU寄存器

CCU寄存器位于CCU硬件内部，包括地址寄存器、通用寄存器和同步寄存器。三类寄存器分别承担以下作用：

- 地址寄存器保存CCU数据搬运所需的GM地址，并支持根据地址偏移更新数据位置。
- 通用寄存器保存通信任务使用的数据，例如通信内存地址、`Token`、数据长度等。CCU可以从本端GM将这些数值加载到通用寄存器，也可以将通用寄存器中的数值写回本端GM。
- 同步寄存器包含多个事件位，每个事件位表示一个需要等待的条件，例如数据搬运完成、前序任务完成或对端通知到达。条件满足后，对应的事件位被置位，CCU随后继续执行。

在需要通过寄存器交换远端GM地址和`Token`的CCU算子编排中，读写双方按以下过程传递参数并进行同步：

- 被访问GM所在的一方通过Channel，将通信内存的地址和`Token`分别写入读写发起方的通用寄存器，并置位双方约定的通知事件。
- 读写发起方等待通知事件，读取地址和`Token`，将地址装入地址寄存器，并使用地址和`Token`访问对端GM。
- 数据搬运完成后，读写发起方可以置位对端的通知事件，告知对端数据已经就绪或本轮搬运已经完成。

CCU任务通过寄存器传递通信参数和同步状态，通信的用户数据通过GM或CCU Buffer相关的数据路径传输。
