# AICPU API 文档逐页评审约束

本文沉淀 AICPU Asccomm API 文档逐页检查和修改的通用约束。约束适用于 `docs/zh/api/aicpu/asccomm/` 下的 23 个 API 文档；`asccomm_batch_mode_start` 的评审过程仅作为参考案例，不是本文的唯一适用对象。

## 1. 对话和修改流程约束

- 在讨论具体接口时，先阅读现有文档、公开头文件、实现代码、测试和相邻文档，再输出修改方案或“无需修改”的结论。
- **用户确认前不直接修改 API 文档。**修改方案需列出拟修改内容、拟保留内容、修改依据，以及无法确认的遗留问题。
- 用户确认后，只修改已确认的范围。评审中发现的新问题单独说明，经确认后再处理，不顺手扩大修改范围。
- 对实现行为、错误码、参数范围、协议差异和代码常量的描述，必须有代码或仓库内权威资料支撑；不能凭相似接口推断。
- 不能由当前证据确认、又可能属于产品契约的信息，不写入正式 API 文档，记录到 `API_REVIEW_OPEN_ISSUES.md` 或当次评审记录中。
- 修改后检查最终 Markdown、链接目标、函数原型与头文件一致性，并执行 `git diff --check`。

## 2. 内容表达约束

- 功能说明从用户视角出发，先说明接口用途和调用后的可感知行为，再说明必要的使用条件。
- 首段避免暴露 SQE、Thread 登记列表、内部缓存归属等实现细节；只有当实现细节影响用户调用方式或正确性时，才放入约束说明并说明因果。
- 描述保持简洁。用户不需要为了使用 API 而理解所有内部机制；文档应说明“做什么、什么时候生效、和哪些接口配合、返回什么”。
- 概念只在首次出现或容易混淆时解释。例如“当前AICPU执行线程”用于说明作用范围和成对调用要求，不应反复展开。
- 禁止绝对化但不符合实现的说法，如“所有数据面接口调用都不会立即执行”。应改成有边界的行为描述，如“需要下发的通信任务会先缓存”。
- 来自实现细节或代码常量、尚未确认是否为长期契约的行为，使用“当前实现中”限定。例如缓存容量、提前提交、特定协议 no-op 行为。
- 约束必须是调用方需要遵守或需要知晓的行为，并与代码证据一致。不要把普通实现细节包装成用户约束。
- 示例注释必须与真实语义一致。如果行为是“先缓存、End 时统一提交”，注释不能写成“不会立即执行”。
- 返回值表只列当前接口实际可达的取值，或明确说明是异常兜底；不照搬其他数据面接口的通用错误码列表。
- 每个返回值给出具体含义，例如成功代表什么动作成功、失败代表哪类问题，避免只罗列错误码名称。

## 3. 结构和格式约束

- API 页面保持标准章节顺序：产品支持情况、功能说明、函数原型、参数说明、返回值说明、约束说明、调用示例。可选章节仅在无内容时省略。
- 函数原型、参数名、参数类型、返回类型必须与公开头文件严格一致。
- 参数说明写清输入/输出、取值范围、单位、有效条件和特殊值；保留参数需说明当前实现是否读取和校验。
- 返回值章节先用一句话说明返回类型，再接取值表；不使用 `int32_t：` 后直接接表格的形式。
- 表格、代码块、中文标点、相对链接和过滤标签遵循仓库 API 文档规范。
- 修改保持最小局部变更，不引入无关格式化、不改无关接口文档。

## 4. 逐页检查清单

对每个 API 文档，按以下顺序检查：

1. 文档结构与导航是否正确，链接是否可解析。
2. 函数原型、参数、返回类型是否与公开头文件一致。
3. 功能说明是否符合用户视角，是否简洁、准确、无过度实现细节。
4. 参数说明是否覆盖取值范围、单位、保留参数和特殊值。
5. 返回值是否只列本接口可达取值，含义是否具体。
6. 约束是否为用户需要遵守或知晓的行为，是否有代码证据。
7. 调用示例是否只使用公开接口，参数是否正确，注释是否与行为一致。
8. 不确定信息是否已记录为遗留问题，而不是写入正式文档。

## 5. `asccomm_batch_mode_start` 参考案例

该案例形成了以下通用经验：

- 原描述把 SQE、Thread 登记、本地缓存放在首段，用户理解成本高；最终改为“开启当前AICPU执行线程的批量提交模式，需要下发的数据面通信任务先缓存，End 时统一提交”。
- “所有数据面接口调用都不会立即执行”不准确：不是所有接口都会生成需要下发的通信任务，且内部缓存满时会提前提交。
- 通用错误码列表不适合所有接口。`asccomm_batch_mode_start` 当前没有参数、指针和 not support 错误分支，不应列 `ASCCOMM_E_PARA`、`ASCCOMM_E_PTR`、`ASCCOMM_E_NOT_SUPPORT`。
- `int32_t：` 后直接接表格不自然；应改为“返回值为`int32_t`，取值含义如下。”再接表格。
- “缓存容量为128”来自代码常量，应作为当前实现行为放在约束说明中，不写成无条件的长期契约。

## 6. 近期逐页修改补充

近期对批量操作和本地拷贝接口的逐页评审进一步形成以下要求：

- 功能说明应先说明接口用途和生效时机。批量接口需要明确任务何时缓存、何时提交，避免在首段展开SQE、本地缓存或Thread登记等内部实现。
- `ThreadHandle`和`ChannelHandle`参数使用统一表述：由控制面创建资源，作为AICPU Kernel参数传入，调用时不能为0，并注明类型定义头文件。
- 返回值表只列当前接口代码路径实际可达的错误码。每个错误码都要说明对应场景；没有实现分支的错误码不能因为其他接口使用过就一并列出。
- 约束说明只保留调用方需要遵守或知晓的内容。重复条目应删除，内部实现细节不应直接包装成用户约束；无法确认的边界行为（例如4GiB分片边界）记录到遗留问题文档。
- 协议支持、产品支持和特殊行为必须有当前实现或其他权威资料依据，不能根据相邻接口或旧仓库文档直接推断。
- 调用示例可以保持简洁，使用前置流程准备好的Thread、Channel和Device地址即可，不重复展示资源创建。示例不得使用栈内存或`malloc`替代Device地址，注释必须与接口的异步或批量提交语义一致。
- 每个接口仍按“先核对、再输出方案、用户确认后修改”的流程处理；修改后同步更新Todo进度，只改动已确认的文件和范围。

## 7. 输出方案模板

每次逐页评审时，方案按以下结构输出：

```markdown
### 事实核对结论
- 说明文档与头文件、实现、测试的核对结果。

### 拟修改内容
- 按章节列出拟修改后的文字或表格。
- 说明每处修改的代码或规范依据。

### 拟保留内容
- 说明哪些现有内容不需要修改，以及原因。

### 遗留问题
- 列出无法由当前证据确认、需要产品或代码负责人确认的问题。

### 修改范围
- 明确仅修改当前 API 文档，不涉及其他页面。
```
