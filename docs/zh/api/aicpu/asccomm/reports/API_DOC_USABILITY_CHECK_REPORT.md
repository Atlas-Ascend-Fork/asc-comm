# AICPU Asccomm API文档可用性检查报告

## 1. 检查范围

- 检查对象：23个AICPU Asccomm API页面。
- 参考skill：`api-doc-check`。
- 检查视角：AICPU通信算子开发者能否按文档正确调用这些数据面接口。
- 检查时间：2026-09-30 15:30 Asia/Shanghai。

## 2. 总体结论

23个API的参数、返回值、函数原型和调用示例已经能支持开发者理解接口本身的使用方式。文档中不再混入旧HCOMM控制面调用，数据面调用示例聚焦明确。

当前存在4类可能阻塞实际开发的信息缺口，均不是单个API页面的格式问题，而是缺少控制面资源构造说明或产品/协议支持矩阵：

1. Thread和Channel资源的构造与下发流程缺失；
2. 产品支持矩阵未确认；
3. 芯片与协议组合未确认；
4. Channel Notify Wait本地索引布局需确认。

## 4. 阻塞问题

### 阻塞-1：缺少Thread和Channel资源构造说明

- **表现**：所有需要`ThreadHandle`或`ChannelHandle`的API都说明“控制面构造并随AICPU Kernel参数下发”，但asc-comm仓没有对应控制面API文档。
- **影响**：开发者知道数据面如何调用，但无法从当前文档体系完成资源准备。
- **建议**：迁移或链接AICPU控制面资源创建文档，并在README中说明数据面和控制面配合流程。

### 阻塞-2：产品支持矩阵未确认

- **表现**：23个页面均沿用模板化产品支持状态，但当前数据面代码没有芯片分支。
- **影响**：开发者无法确定目标芯片是否可用。
- **建议**：由产品矩阵或硬件验证结果确认后更新。

### 阻塞-3：芯片与协议组合未确认

- **表现**：文档只说明UB/RoCE协议行为，不承诺具体芯片和引擎组合。
- **影响**：开发者无法确定在目标产品上应选择AICPU_TS、CPU_TS、UB还是RoCE路径。
- **建议**：控制面建链能力和产品矩阵确认后补充推荐组合。

### 阻塞-4：Channel Notify Wait索引布局不明确

- **表现**：文档写为“小于可用于等待的本地Notify数量”，但控制面`notifyNum`与资源实体中`localNotifyNum`的映射未说明。
- **影响**：开发者可能传入错误索引，导致参数错误或等待错误Notify。
- **建议**：控制面确认数组布局后在参数说明中给出精确取值范围。

## 5. 非阻塞提示

1. `asccomm_read_reduce_on_thread`在RoCE通道上不执行数据操作但返回成功，开发者容易误以为数据已更新；建议在总览或接口页增加显著警告。
2. `asccomm_channel_drain_on_thread`在RoCE通道上直接返回成功，应提醒用户需要依赖其他完成机制。
3. `asccomm_batch_transfer_on_thread`当前仅支持UB类协议，RoCE场景应提前判断，避免误用。
4. 超时小数会向零截断，虽然已写入文档，但建议示例统一使用整数浮点值，减少误解。

## 6. 结论

接口页面的局部可用性较好，但完整开发链路仍被控制面资源文档和产品支持矩阵阻塞。建议先补齐资源构造与下发说明，再闭环产品/协议矩阵。
