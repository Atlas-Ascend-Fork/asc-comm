# CCU同步接口文档方案概述

本文档说明 `event_record`、`event_wait`、`notify_record`、`notify_wait`、`write_variable_with_notify` 五个同步接口文档的设计方案，包括术语体系、公共机制与各接口的关键表述决策，供评审与后续维护参考。

## 一、术语体系

同步接口的核心概念是信号的**二维定位**，各维度有专名，全部锚定在[CCU编程](../../../programming_model/ccu_programming.md)的"同步机制"节：

| 术语 | 含义 | 由谁选择 |
| --- | --- | --- |
| CKE单元 | CKE同步寄存器中的物理单元，每单元16个标志位 | 物理统称 |
| event单元 | `event`对象构造时分配绑定的CKE单元，本端同步用 | 对象封装，接口只见`mask` |
| notify单元 | channel建链时两端各预留的镜像编号CKE单元（最多8个），跨端信号用 | `idx`参数显式指定（0~7） |
| 标志位 | 单元内的16个bit | `mask`参数（第i位为1即选中第i个标志位） |

- Event与Notify使用同一种CKE资源：Event操作本端单元，Notify置位对端单元。
- 端侧统一用"本端/对端"（不用"本地/远端"）；生产/消费沿用synchronization/README的定义。
- 已弃用词：槽位、事件单元、完成事件单元、运行期。

## 二、公共机制

所有接口共享以下表述基础：

1. **两阶段**：接口调用发生在注册阶段（Host执行Kernel函数体，调用被记录为指令），硬件动作发生在执行阶段。
2. **信号模型**：record类接口置位标志位，wait类接口阻塞等待标志位置位。
3. **配对语义**：生产侧置位、消费侧等待，`mask`须两侧一致。
4. **异常路径**：接口抛出的异常由`HcommCcuKernelRegister`统一接住，调用方无须自行捕获。

## 三、各接口方案

### event_record：显式置位本端信号

- **定位**：将本端同步寄存器中`mask`对应的event单元标志位显式设置为1，供同kernel内的event_wait等待。不阻塞执行。
- **关键决策**：
  - "显式"与数据搬运接口的自动置位形成对照，是该接口存在的意义；
  - 置位时机为"执行到该指令时"，是位置标记而非完成验证，不可用于替代搬运完成信号；
  - NOTE只讲增量信息（同步点处无数据搬运时才需显式调用）。
- **约束**：两条真禁令——不可在硬件loop循环体内调用（返回`CCU_E_NOT_SUPPORT`硬拦截）；`mask`须与event_wait一致。
- **删除的错误**：原"record必须有对应wait，否则死锁"因果方向是反的（wait无record才死锁），该约束归event_wait。

### event_wait：阻塞等待本端信号

- **定位**：阻塞等待本端同步寄存器中`mask`对应的event单元标志位，直到全部为1后继续执行，随后自动清零。
- **关键决策**：
  - 信号来源双通道：同kernel内的event_record，或数据搬运接口的末位参数`(event, mask)`自动置位；
  - 配对语义集中在功能说明的NOTE：单次一次性（等待成功自动清零，须重新置位才能再次等待）+ 同一event的不同mask相互独立可承载多组配对；
  - 约束仅留两条真禁令：等待的信号须已有来源（否则永久阻塞、硬件级死锁）；`mask`须与生产侧一致。
- **参数说明**：`e`行带CKE桥接（"对应CKE同步寄存器中的一个event单元"）；`mask`行与event_record句式平行（"指定要等待的event单元标志位…即bit0…`mask = 0x3`表示等待bit0和bit1全部置位"）。

### notify_record：向对端发送信号

- **定位**：通过channel向对端die发送完成信号，将对端同步寄存器中`mask`对应的notify单元标志位设置为1，供对端的notify_wait等待。
- **关键决策**：
  - 跨die适用范围（同device其他die、跨device、跨节点，路径由硬件自动选择）只在本接口说明一次，notify_wait不重复；
  - 删除实现细节：die-to-die信号包、HCCS/RDMA路由。
- **约束**：不可在硬件loop循环体内调用属软禁令（接口不拦截，但循环体被复制为多份并行执行时信号会被重复发送，应避免）；die一致性由`HcommCcuKernelRegister`统一校验；notify单元编号由两端开发者约定，框架不校验。
- **参数说明**：`remote_notify_idx`为对端notify单元索引，取值0~7。

### notify_wait：阻塞等待对端发来的信号

- **定位**：阻塞等待本端同步寄存器中`mask`对应的notify单元标志位，该标志位由对端die的notify_record通过channel置位。
- **关键决策**：
  - 功能说明与event_wait句式平行（动作句+来源句），仅端侧与来源不同；
  - 不写清零语义（与event_wait的差异处，机制未确认，不臆造）。
- **参数说明**：`local_notify_idx`为本端notify单元索引，取值0~7，须与发送侧的`remote_notify_idx`使用相同数值。

### write_variable_with_notify：写值与通知的原子操作

- **定位**：将"写对端variable值"与"触发对端notify"合并为单条原子操作，硬件保证"先写值后发通知"的顺序。消费侧通过notify_wait等待信号，再通过`get_res_by_channel`读取新值。
- **关键决策**：
  - CAUTION强调不可拆分为两步调用：硬件不保证两条独立操作的到达顺序，拆分会使消费侧存在读到旧值的风险；
  - 槽位约定的通俗化表述：编号由两端kernel各自传入，框架不分配也不校验，须由开发者保证两端一致，不一致则消费侧永久阻塞；
  - 单元术语：对端variable单元索引（`get_res_by_channel`引用同一单元）+ 对端notify单元索引。
- **约束**：不可在硬件loop循环体内调用；die一致性；两个单元编号的两端一致性。

## 四、结构与表述规范

- **章节模板**：产品支持情况 / 功能说明 / 函数原型 / 参数说明 / 返回值说明 / 约束说明 / 调用示例。
- **功能说明**：动作直述开头，不用名词定位（如"消费者侧接口"）；record类以动作+消费方收尾，wait类以动作+来源收尾。
- **参数说明**：取值范围入参数行；避免括号插入语；标志位标准句式"自动将`event`中`mask`对应的标志位设置为1"。
- **约束说明**：只列真禁令与前置条件；能力描述（如多组配对）归功能说明的NOTE。
- **调用示例**：`my_kernel`/`my_kernel_arg`命名；成对示例（生产侧与消费侧两个kernel）展示端到端用法；注释统一"每次下发时从task_args加载"口径。

## 五、待确认项
