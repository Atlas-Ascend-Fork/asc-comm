# 内存模型章节整改方案

## 1. 背景与目标

当前《内存模型》先介绍内存层级和通信能力，随后按 HComm、CCU 和 AIN 分别介绍本地与远端内存可见性。后半部分以编程接口为组织主线，引入了 ChannelHandle、RemoteAddr、Team、Window Handle 以及访问凭据的具体承载形式等较多接口和实现概念，与编程指南前部章节应先建立基础概念的定位不一致。

本次整改的目标是：

- 以“内存位于哪里、谁可以访问、如何对远端可见”为主线，不以编程接口为主线。
- 先介绍内存层级和通信能力，再按通信内存、L2 Cache、Unified Buffer、Memory Slice 和片内寄存器展开。
- 使用同一组上层概念覆盖 AICPU HComm、AI Core HComm、CCU 和 AIN，不展开具体接口调用和算子实现。
- 使用户阅读本章后能够理解通信内存、本地与远端可见性、访问凭据、显式远端寻址、对称窗口、缓存一致性与通信完成等必要概念。

本文档基于 `asc-comm`、`hcomm` 和 `asc-devkit` 三个代码仓的源码与公开文档进行核对，先给出实现确认结论，再给出正式章节的整改结构。

## 2. 实现确认结论

### 2.1 总体结论

“先总览，再按内存资源展开”的整体思路正确，可以统一覆盖当前几种编程范式。正式章节建议采用以下叙述链路：

```text
物理内存层级
    -> GM 中用于通信的数据范围
    -> 本地可见与远端可见
    -> 远端访问凭据与授权
    -> 显式远端寻址与对称窗口寻址
    -> L2 Cache 及缓存一致性边界
    -> AI Core 和 CCU 的片内资源
```

经过实现核对，原方案需要补充以下修正：

1. 对称和非对称描述的是通信内存的组织与寻址方式，不是 HComm、CCU 或 AIN 执行引擎本身的属性。建议使用“显式远端寻址（非对称组织）”和“对称窗口寻址”。
2. “通信内存位于 GM”必须限定为本章讨论的 Device 侧通信数据。HCOMM 通用资源接口也支持 Host 内存，不能将“所有 HCOMM 通信内存均位于 GM”写成无条件结论。
3. L2 Cache 与 GM 之间由硬件维护一致性，不代表各核私有 DCache、SIMT DCache 不会保留旧副本，也不代表通信操作已经完成。正文必须把缓存副本、访问完成和执行顺序分开说明。
4. 当前公开 CCU 数据面支持本端 GM、本端 Memory Slice 和对端 GM 之间的数据搬运，也支持写远端 Variable/Notify；没有公开的“直接访问对端 Memory Slice”操作数。现稿相关表述需要收缩。
5. 当前源码不能证明 AI Core UB 与 CCU Memory Slice 是对用户开放的通用直连地址空间。大图可以保留硬件能力视图，但图注必须区分“公开编程能力”和“内部或硬件通路”。
6. Key 和 Token 是远端访问保护的协议机制，不应整体下沉。正式正文应解释凭据如何与注册内存范围绑定并参与传输校验；字段格式、获取接口和参数承载方式再下沉。
7. 显式远端寻址和对称窗口寻址不能只给定义，还应分别说明用户可见的内存组织、访问位置表达，以及运行时如何解析到实际 GM。

### 2.2 Device GM 与通信内存

#### 实现确认

HCOMM 使用 `CommMem` 描述一段内存，其元数据包含内存类型、地址和大小。通信域侧保存 HcclBuffer 和用户登记的内存；创建 Channel 时，HcclBuffer 会被加入待注册内存集合，用户选择的内存句柄也会加入该集合。随后内存通过 Endpoint 注册，并随 Channel 建立过程形成本地和远端注册内存信息。

设备侧 `ChannelEntity` 分别保存 `localBufferAddr` 和 `remoteBufferAddr`。每个注册内存表项除了地址和大小，还保存 RoCE 的 `lkey/rkey` 或 UB 类协议的 `tokenId/tokenValue`。这说明“通信内存”不是新的物理内存层级，而是被纳入通信关系并具有访问元数据的内存范围。

实现依据：

- [`HcclChannelDesc` 关联远端 rank 和待交换内存句柄](../../../../hcomm/include/hccl/hccl_res.h#L40)。
- [HcclBuffer 与用户内存共同组成 Channel 的待注册内存集合](../../../../hcomm/src/coll_communicator_mgr/resource_mgr/local/my_rank/comm_mems/comm_mems.cc#L190)。
- [创建 Channel 前通过 Endpoint 注册上述内存](../../../../hcomm/src/coll_communicator_mgr/resource_mgr/local/my_rank/my_rank.cc#L490)。
- [`RegedBufferEntity` 保存地址、大小和协议保护信息](../../../../hcomm/pkg_inc/hcomm/hcomm_res_entity_defs.h#L56)。
- [`ChannelEntity` 分别保存本地和远端注册内存表](../../../../hcomm/pkg_inc/hcomm/hcomm_res_entity_defs.h#L170)。

#### 对正式正文的约束

正式正文可以写：

> 本章中的通信内存特指 Device 侧用于通信数据的 GM 范围。通信内存不是独立于 GM 的物理层级，而是已经纳入通信管理、能够作为通信操作数的 GM 范围。

同时需要给出范围声明：HCOMM 通用资源层还可以管理 Host 内存，但 Host 内存不属于本章大图和 Device 编程模型的讨论范围。

不建议在正式正文中出现 HcclBuffer 注册接口、内存句柄、Endpoint 注册或协议保护字段。

### 2.3 本地与远端可见性

#### 实现确认

AICPU HComm 和 AI Core HComm 的通信操作都显式使用 Channel、本地地址和远端地址。AI Core HComm 在发起通信前，会根据远端地址和访问长度查找当前 Channel 的远端注册内存表；RoCE 路径取得远端 `rkey` 和本地 `lkey`，UB/URMA 路径取得远端 Token 并写入通信描述符。

因此，只有一个数值地址并不足以访问远端内存。有效远端访问至少依赖以下信息：

- 通往目标通信成员的通信关系。
- 对端内存的实际地址和有效范围。
- 与该范围匹配的访问凭据。

实现依据：

- [AI Core HComm 按地址和长度匹配注册内存范围](../../../src/aicore/hcomm/common/hcomm_utils.h#L72)。
- [RoCE 路径从 Channel 的本地、远端内存表取得 lkey 和 rkey](../../../src/aicore/hcomm/impl/platform_v310/hcomm_aiv_roce.h#L111)。
- [UB/URMA 路径匹配远端内存表并使用其中的 Token](../../../src/aicore/hcomm/impl/platform_v310/hcomm_aiv_urma.h#L332)。
- [公共注册内存描述将地址、大小和协议保护信息绑定](../../../../hcomm/pkg_inc/hcomm/hcomm_res_entity_defs.h#L56)。
- [RoCE 注册内存描述可以导出，并在对端导入为远端内存对象](../../../../hcomm/src/base_comm/resources/reged_mems/roce_mem.cc#L78)。
- [UB 注册内存描述可以导出，并在对端导入为远端内存对象](../../../../hcomm/src/base_comm/resources/reged_mems/urma_mem.cc#L84)。

#### 对正式正文的约束

正式正文应只保留以下上层语义：

- 本地可见表示当前执行引擎可以把该地址作为本地操作数。
- 远端可见表示通信对端已经获得目标内存的地址范围和访问授权，并能通过已建立的通信关系访问。
- 本地可见不等于远端可见。
- 远端地址不是本端可以直接解引用的普通地址。
- 地址和长度必须完整落在已开放范围内。

在这些上层语义之后，需要继续介绍“远端访问授权机制”，而不能把 Key 和 Token 整体下沉。建议按以下层次说明：

1. 地址用于定位内存，访问凭据用于证明本次访问已被目标内存授权。只有远端地址、没有匹配凭据，不能形成有效的远端访问。
2. 内存纳入通信管理时，通信协议为相应内存范围建立访问保护信息。凭据与已注册的内存范围绑定，并在已建立的通信关系中被关联使用，不能脱离对应范围任意混用。
3. 建立通信关系时，本端和对端交换或关联远端内存描述，使发起端获得访问目标内存所需的信息。
4. 发起数据传输时，通信协议根据操作涉及的地址范围选择相应凭据，并由通信硬件或协议执行访问校验。

不同协议的凭据机制可以在正文中概括为：

| 协议类型 | 凭据机制 | 机制级职责 |
| --- | --- | --- |
| RoCE | 本地 Key 和远端 Key | 本地 Key 授权通信引擎读取或写入本端内存，远端 Key 授权访问对端开放的内存范围 |
| UB 类协议 | 内存导出/导入信息和 Token | 导出/导入信息用于建立远端内存关系，数据传输时使用与目标内存范围绑定的 Token 进行访问校验 |

正文不展开 Key/Token 的数值结构、字段编码、获取接口、交换接口、描述符装载方式，也不介绍 `LocalAddr`、`RemoteAddr` 如何承载地址和凭据。这些内容仍下沉到接口或算子实现章节。

### 2.4 显式远端寻址（非对称组织）

#### 实现确认

AICPU HComm、AI Core HComm 和 CCU 的公开数据面虽然使用不同的地址表示，但共同点是调用方需要围绕特定对端建立通信关系，并提供或准备该对端的远端操作数。

HComm 使用 Channel 和本地、远端地址；访问凭据由 Channel 内的注册内存表提供。CCU 的 `LocalAddr` 和 `RemoteAddr` 均由 Address 和 Variable 组成，Variable 用于承载 Token；Host 侧可以为一段合法内存查询 CCU Token。CCU 的远端读写原语同时使用 Channel、`LocalAddr`/`RemoteAddr`。

实现依据：

- [`LocalAddr` 由 Address 和 Variable 组成](../../../../hcomm/include/ccu/ccu_local_addr.hpp#L24)。
- [`RemoteAddr` 由 Address 和 Variable 组成](../../../../hcomm/include/ccu/ccu_remote_addr.hpp#L24)。
- [CCU 为地址范围查询访问 Token](../../../../hcomm/include/ccu/ccu_res.h#L117)。
- [CCU 跨 rank 原语使用 Channel、本地操作数和远端操作数](../../../../hcomm/include/ccu/ccu_primitives.hpp#L93)。

#### 对正式正文的约束

建议使用“显式远端寻址（非对称组织）”，其定义是：

> 各通信成员分别管理自己的内存。访问远端内存前，需要面向目标成员建立通信关系，并获得或准备与该成员匹配的远端地址范围和访问授权。各成员的数值地址和内存布局不要求相同。

HComm 和 CCU 只作为这种组织方式的例子出现，不分别展开章节。不能简单写成“HComm/CCU 是非对称内存”，因为二者是编程接口或执行方式，不是内存类型。

除定义外，还需要从用户视角说明该机制如何呈现：

- 各成员独立准备和管理本端通信内存，因此不同成员的内存大小、布局和数值地址可以不同。
- 用户在建立通信关系时，需要为特定对端关联可访问的远端内存；访问时需要明确选择目标成员及其远端内存位置。
- 运行时根据目标成员选择对应通信关系，将远端位置与已经关联的内存范围和访问凭据匹配，再发起传输。
- 用户能够感知“面向哪个成员、访问哪段远端内存”，但不需要在本章理解 Channel、`LocalAddr`、`RemoteAddr` 等对象如何封装这些信息。

建议在正式正文中使用一幅不含接口名的机制图：

```text
目标成员 + 远端内存位置
          -> 选择面向该成员的通信关系
          -> 匹配远端内存范围和访问凭据
          -> 访问该成员的实际 GM
```

### 2.5 对称窗口寻址

#### 实现确认

AIN 的 Device 侧实现通过 Team 保存的成员信息选择 peer Channel，通过 Window 中 `mems[memberId]` 保存的实际 `CommMem` 和 offset 计算本地或远端 GM 地址。`Put` 和 `Get` 完成地址解析后，继续调用底层 AI Core HComm 的 `WriteNbi` 或 `ReadNbi`。

这说明 AIN 的对称性是逻辑组织和寻址语义的对称：各成员使用同一个逻辑窗口以及成员和偏移描述对应内存，不要求各成员的数值地址相同。窗口也没有替代 Channel 或访问授权。

HCOMM 控制面还提供对称窗口登记能力，并会在特定 Channel 建立流程中将待处理的对称内存句柄合入 Channel 的内存集合。该流程可以证明“对称窗口仍需参加底层内存注册和交换”，但不能直接视为 AIN Team/Window 的创建实现；当前三个仓中没有发现 AIN Team/Window 完整控制面创建代码。

实现依据：

- [AIN 的 Window 和 Team 是 Device 侧不透明句柄](../../../include/aicore/ain/ain_common.h#L28)。
- [AIN 按成员和 offset 从 Window 解析实际 GM 地址](../../../src/aicore/ain/impl/ain_impl.h#L40)。
- [AIN 按 peer 从 Team 选择 Channel](../../../src/aicore/ain/impl/ain_impl.h#L30)。
- [AIN Put 解析地址后调用 AI Core HComm WriteNbi](../../../src/aicore/ain/impl/ain_impl.h#L90)。
- [AIN Get 解析地址后调用 AI Core HComm ReadNbi](../../../src/aicore/ain/impl/ain_impl.h#L146)。
- [HCOMM 将对称内存句柄合入 UB/URMA Channel 的内存集合](../../../../hcomm/src/coll_communicator_mgr/api_c_adpt/coll_comm_res_c_adpt.cc#L370)。

#### 对正式正文的约束

建议将对称窗口定义为：

> 对称窗口把各通信成员的一段对应内存组织为同一个逻辑对象。程序通过目标成员和窗口内偏移定位本地或远端内存，不需要在每次操作时直接管理远端裸地址。对称表示逻辑布局和寻址方式一致，不表示各成员的数值地址必须相同。

正文还应说明：窗口只简化地址组织，底层仍需建立通信关系、关联实际地址范围和访问授权。

还应从用户视角解释窗口如何形成可见的寻址对象：

- 各成员分别提供一段本端通信内存，这些对应内存被共同组织成一个逻辑窗口。
- 用户看到的是同一个窗口及其成员关系，访问时通过“目标成员 + 窗口内偏移”描述位置，不需要逐次处理该成员的远端裸地址。
- 运行时先根据目标成员选择对应通信关系，再将窗口内偏移解析为该成员的实际 GM 地址，并匹配该内存范围的访问凭据。
- 因此，对称性体现在各成员使用一致的逻辑组织和寻址规则；各成员的实际地址仍可不同，底层访问保护也不会因窗口抽象而省略。

建议在正式正文中使用与显式远端寻址并列的机制图：

```text
逻辑窗口 + 目标成员 + 窗口内偏移
          -> 选择该成员对应的通信关系和窗口内存
          -> 解析实际 GM 地址并匹配访问凭据
          -> 访问该成员的实际 GM
```

Team、Window Handle、peer 到 Channel 的映射以及 AIN 原语参数均不在本章展开。

### 2.6 L2 Cache 与缓存一致性

#### 实现确认

`asc-devkit` 的平台编程文档明确说明：L2 Cache 是核外共享缓存，多个核共享同一 L2 Cache，不需要处理多个核之间的 L2 副本不一致；L2 Cache 与 GM 之间的一致性由硬件保证。

同一份 GM 数据仍可能存在于各核独立的 DCache 或 SIMT DCache 中。生产者的新值可能尚未完成写回，消费者也可能命中本核旧副本。缓存一致性、访问完成和执行顺序是三个不同问题，DCCI、DSB 和同步通知不能互相替代。

`asc-comm` 的 AI Core HComm 实现也会对由 Scalar 写入的队列描述符执行 Cache clean/invalidate，说明通信实现本身不能把所有缓存层级简化为“L2 与 GM 一致，所以无需缓存处理”。

实现与平台依据：

- [L2 Cache 是多个核共享的核外缓存](../../../../asc-devkit/docs/zh/guide/编程指南/高级编程/内存模型/缓存一致性.md#L16)。
- [同一份数据可能同时存在于 GM、L2、DCache 和 SIMT DCache](../../../../asc-devkit/docs/zh/guide/编程指南/高级编程/内存模型/缓存一致性.md#L38)。
- [缓存一致性与内存访问顺序是不同问题](../../../../asc-devkit/docs/zh/guide/编程指南/高级编程/内存模型/缓存一致性.md#L65)。
- [L2 与 GM 一致不代表预取的数据必然是期望的新值](../../../../asc-devkit/docs/zh/guide/编程指南/高级编程/内存模型/缓存一致性.md#L640)。
- [AI Core HComm 对队列内存执行 Cache clean/invalidate](../../../src/aicore/hcomm/common/hcomm_utils.h#L101)。

#### 对正式正文的约束

正式正文建议只写四点：

1. L2 Cache 缓存本 Device 的 GM 数据，并由多个核共享。
2. L2 Cache 与 GM 之间的一致性由硬件保证。
3. 该保证不覆盖各核独立的 DCache 或 SIMT DCache 旧副本，也不等价于通信完成。
4. 消费数据前仍需根据实际生产和消费路径完成必要的缓存处理、完成等待和执行顺序同步；具体接口在缓存一致性和算子实现章节介绍。

现稿中“远端写事务进入并更新目标侧 L2 Cache，因此不需要额外操作”的表述不宜保留。远端写入的精确落点和缓存策略需要硬件规格确认；本章只陈述已经由平台文档确认的 L2/GM 一致性边界。

### 2.7 Unified Buffer

#### 实现确认

`asc-devkit` 将 UB 定义为 AI Core 内部、服务 Vector 计算的片内存储，典型数据流为 `GM -> UB -> Register` 或 `GM -> UB`。AI Core HComm 和 AIN 还需要调用方提供一段 UB 工作区，用于组装通信描述符等内部操作。

这些实现支持将 UB 介绍为 AI Core 片内暂存与通信工作区，但不支持把 UB 定义为可直接对远端开放的通信内存。

实现与平台依据：

- [AI Core SIMD 采用显式分层访存，数据在 GM 与片内存储间搬运](../../../../asc-devkit/docs/zh/guide/编程指南/编程模型/AI-Core-SIMD编程/概述.md#L33)。
- [Ascend 950 的 Vector 数据流包含 GM、UB 和 Register](../../../../asc-devkit/docs/zh/guide/编程指南/编程模型/AI-Core-SIMD编程/概述.md#L48)。
- [AIN 使用调用方提供的 UB 工作区初始化底层 HComm](../../../src/aicore/ain/impl/ain_impl.h#L90)。

#### 对正式正文的约束

正文介绍 UB 的位置、作用和范围即可：

- UB 是 AI Core 的片内高速存储。
- UB 用于计算数据暂存，也可作为通信实现的工作区。
- UB 容量和生命周期不同于 GM。
- UB 不是本章定义的通信内存，不因本地 AI Core 可访问而自动对远端可见。

SIMD/SIMT 的申请语法、容量划分和寄存器接口留在相应编程章节。

### 2.8 Memory Slice 与 CCU 寄存器

#### 实现确认

CCU 以 `CcuBuffer` 表示本端 Memory Slice。公开原语支持：

- 本端 GM 与本端 Memory Slice 双向搬运。
- 对端 GM 读取到本端 Memory Slice。
- 本端 Memory Slice 写入对端 GM。
- 本端 GM 与对端 GM 直接搬运。
- 多个本端 Memory Slice 参与本地归约。

`LocalAddr` 和 `RemoteAddr` 表示 GM 操作数，不表示 Memory Slice。公开接口没有 `RemoteCcuBuffer` 一类远端 Memory Slice 操作数。因此，Memory Slice 是 CCU 的本地片内中转和归约资源，不应写成通用的跨 Device 可见内存。

CCU 的 Variable、Address 和 Event 分别对应通用、地址和同步资源。`WriteVariableWithNotify` 可以通过 Channel 写远端 Variable 并触发远端 Notify，说明部分远端寄存器资源具备专用通信操作，但不能由此推广为“所有远端寄存器均可像 GM 一样寻址”。

实现依据：

- [`CcuBuffer` 分配 CCU 片内 Buffer 资源](../../../../hcomm/include/ccu/ccu_buffer.hpp#L24)。
- [CCU 公开原语覆盖本端 GM、CcuBuffer 和对端 GM 的搬运](../../../../hcomm/include/ccu/ccu_primitives.hpp#L73)。
- [CCU Kernel 分别分配 Buffer、Address、Variable 和 Event 资源](../../../../hcomm/src/base_comm/resources/ccu/ccu_kernel/ccu_kernel.cc#L365)。
- [CCU 的远端读写实现只接受 RemoteAddr 作为远端内存操作数](../../../../hcomm/src/base_comm/resources/ccu/ccu_kernel/ccu_kernel.cc#L795)。
- [CCU 支持通过 Channel 写远端 Variable 并发送 Notify](../../../../hcomm/include/ccu/ccu_primitives.hpp#L56)。

#### 对正式正文的约束

Memory Slice 小节建议写：

- Memory Slice 是 CCU 的片内高速暂存资源。
- 它可以作为本端通信操作数，在本端 GM 与对端 GM 之间中转数据，并支持归约。
- Memory Slice 不是 GM，也不是对端可通过普通远端地址直接访问的通信内存。

寄存器只需用一段简述其承载地址、标量、访问元数据和同步状态。具体资源类型、申请方法和跨端同步接口放入 CCU 算子实现章节。

## 3. 正式章节建议结构

### 3.1 内存层级和通信能力

保留现有总览图，先解释本章讨论范围，再用一张简表介绍各层资源。

建议表头为：

| 资源 | 物理位置 | 主要使用者 | 在通信中的作用 |
| --- | --- | --- | --- |
| GM 与通信内存 | Device 全局内存 | AICPU、AI Core、CCU | 保存用户数据和通信数据；已纳入通信管理的范围可作为远端操作数 |
| L2 Cache | Device 核外共享缓存 | Device 内多个核和访问路径 | 缓存 GM 数据 |
| Unified Buffer | AI Core 片内 | AI Core | 计算数据暂存和通信工作区 |
| Memory Slice | CCU 片内 | CCU | 通信数据暂存、中转和归约 |
| 片内寄存器 | 对应执行引擎内部 | AI Core、CCU | 保存计算数据、地址、标量和同步状态 |

总览后只解释两件事：资源的物理层级，以及图中箭头表示的已开放通信通路。不要在总览中引入具体接口对象。

### 3.2 GM 与通信内存

建议叙述顺序：

1. GM 是 Device 侧全局内存，用于保存输入、输出和中间数据。
2. 本章中的通信内存是 GM 中已经纳入通信管理的范围，不是独立物理层级。
3. 普通 GM 可被本地执行引擎访问，但只有建立远端访问关系的范围才可被通信对端访问。
4. 通信内存既可以由通信库提供，也可以来自用户管理的 Device 内存；本章不展开其接口差异。

### 3.3 本地与远端可见性

建议在本节统一定义：

- 本地可见。
- 远端可见。
- 远端可见性需要通信对象、地址范围和访问授权共同成立。
- 远端地址不等同于本地普通指针。
- 地址负责定位，访问凭据负责授权；二者作用不同且缺一不可。

用一条抽象流程替代三套接口流程：

```text
准备本端内存
    -> 注册内存并为内存范围建立访问保护信息
    -> 建立面向对端的通信关系
    -> 交换或关联远端内存描述和访问凭据
    -> 传输时按地址范围匹配凭据并校验访问
```

本节增加“访问凭据”小节，说明 Key/Token 所解决的协议问题：数值地址只能定位内存，不能表达该访问是否获得授权；访问凭据与注册内存范围绑定，并在数据传输时参与校验。协议差异只保留机制级对比：RoCE 使用本地 Key 和远端 Key 分别保护本地、远端内存访问；UB 类协议在建链阶段通过内存描述建立远端内存关系，在数据面通过 Token 校验目标内存访问。

本节不介绍 Key/Token 的字段格式、生成和获取 API、描述符编码与装载，也不介绍 `LocalAddr`、`RemoteAddr` 等接口对象如何携带地址和凭据。

### 3.4 通信内存的组织与寻址

#### 3.4.1 显式远端寻址（非对称组织）

先从用户可见语义介绍：各成员独立管理通信内存，用户需要明确目标成员和该成员的远端内存位置，不同成员的内存布局和数值地址不要求一致。再解释运行机制：运行时依据目标成员选择对应通信关系，把远端位置与已关联的内存范围和访问凭据匹配，然后访问该成员的实际 GM。

用一句话说明 HComm 和 CCU 采用这类编程形态，但不比较其函数参数以及 Channel、`LocalAddr`、`RemoteAddr` 等具体承载形式。

#### 3.4.2 对称窗口寻址

先从用户可见语义介绍：各成员提供的对应通信内存组成同一个逻辑窗口，用户以目标成员和窗口内偏移描述访问位置，不需要逐次管理远端裸地址。再解释运行机制：运行时依据目标成员找到对应通信关系和该成员的窗口内存，将偏移解析为实际 GM 地址，并匹配访问凭据后发起传输。

不引入具体 Handle。重点说明数值地址不要求相同，窗口只统一逻辑组织和寻址规则，不替代底层通信关系、实际地址范围和访问授权。用 AIN 作为对应编程形态的例子，但不展开 Team、Window 和原语参数。

建议使用以下对比表：

| 组织方式 | 用户可见的内存组织 | 用户描述访问位置的方式 | 运行时解析 | 共同约束 |
| --- | --- | --- | --- | --- |
| 显式远端寻址 | 各成员分别管理和描述内存 | 目标成员及其远端内存位置 | 选择该成员的通信关系，并匹配远端范围和凭据 | 均需有效通信关系、地址范围和访问授权 |
| 对称窗口寻址 | 各成员的对应内存组成逻辑窗口 | 目标成员和窗口内偏移 | 选择该成员的通信关系和窗口内存，将偏移解析为实际地址并匹配凭据 | 均需有效通信关系、地址范围和访问授权 |

### 3.5 L2 Cache

按“作用 -> 一致性边界 -> 同步边界”组织：

1. L2 是本 Device 多核共享的 GM 缓存。
2. L2 与 GM 之间由硬件保持一致。
3. 私有 DCache、SIMT DCache 的副本需要结合访问路径处理。
4. 缓存一致不表示通信完成，也不建立生产者和消费者的执行顺序。

本节只给出原则，具体 DCCI、DSB、Fence、Notify 和 Wait 放入缓存一致性、同步模型或算子实现章节。

### 3.6 Unified Buffer

介绍 UB 的位置、用途、容量相对较小、生命周期与 Kernel 相关，以及它不是通信内存。可说明部分 AI Core 通信实现会使用 UB 作为工作区，但不介绍工作区结构和申请接口。

### 3.7 Memory Slice

介绍 Memory Slice 是 CCU 的本地片内暂存和归约资源，可以参与本端 GM 与对端 GM 的数据搬运。明确它不是 GM，也不是普通远端地址空间。

### 3.8 片内寄存器

简要说明：

- AI Core 寄存器承载核内计算数据。
- CCU 地址寄存器、通用寄存器和同步寄存器分别承载地址、标量或访问元数据以及同步状态。
- 寄存器属于对应执行引擎的片内资源，不能作为普通通信内存理解。

AICPU 通用寄存器当前没有必要作为用户可编程内存单独介绍。若大图保留该对象，只需标注为执行引擎内部资源，不进入后续正文。
