# 内存模型第二轮整改方案

## 1. 评审意见归纳

本轮评审意见主要涉及概念抽象、章节范围和内容衔接三个方面。

### 1.1 统一通信内存概念

当前文档将通信内存区分为 HcclBuffer 和用户注册内存，并分别说明二者的准备方式。这种写法将具体内存来源和接口生命周期带入了编程模型章节，容易使用户把两种来源理解为两类不同的通信内存。

本轮修改将不再引入 HcclBuffer。通信内存统一定义为物理上位于 GM、经过控制面准备并能够作为通信操作数的内存范围。正文重点说明控制面为这段内存完成哪些准备，不再区分内存由谁申请和管理。具体的内存申请、注册入口和生命周期由对应接口章节说明。

### 1.2 收缩后半部分的章节范围

当前文档在“通信内存”之后，依次设置了 L2 Cache、Unified Buffer、Memory Slice 和寄存器等并列章节，导致文档从通信内存主线重新回到通用硬件资源介绍，重点不够集中。其中 AI Core 寄存器和 AICPU 通用寄存器还是空章节。

修改后，正文只展开以下两个主体：

1. GM 中的通信内存。
2. CCU 片上内存模型，包括 `CcuBuffer` 和 CCU 寄存器。

L2 Cache 和 UB 只在开头的内存资源总览中简要说明。AI Core 寄存器和 AICPU 通用寄存器不再设置正文小节。

### 1.3 建立通信内存与 CCU 片上资源之间的衔接

通信内存说明跨端传输的数据存放位置、远端可见性、访问授权和上层组织方式；`CcuBuffer` 与 CCU 寄存器说明 CCU 执行通信任务时使用的片上资源。两部分不是两个相互独立的话题，而是 GM 通信数据与 CCU 片上处理资源之间的配合关系。

修改时将在两个主体章节之间增加转场，先收束通信内存的作用，再引出 CCU 如何通过 `CcuBuffer` 暂存、中转和归约数据，以及如何通过寄存器保存搬运参数和同步状态。

## 2. 整改目标

- 通信内存只保留一个上层概念，不再按照 HcclBuffer 和用户注册内存分类。
- 通过控制面的统一处理流程解释一段 GM 如何具备远端可见性。
- 文档主体收敛为“通信内存”和“CCU 片上内存模型”两个部分。
- L2 Cache 和 UB 只提供理解通信数据路径所需的最少信息。
- `CcuBuffer` 和 CCU 寄存器作为 CCU 片上内存模型的两个组成部分连续介绍。
- 保留访问凭据、非对称内存和对称内存等已经建立的通信内存主线。
- 概念章节不展开具体内存申请接口、资源配置和算子实现。

## 4. 具体修改方案

### 4.1 调整开头的资源总览

保留现有内存层级图，用于说明 GM、L2 Cache 和各执行引擎片内资源的物理关系。正文通过图注说明：后文只展开与通信数据组织直接相关的通信内存，以及 CCU 使用的 `CcuBuffer` 和寄存器；图中的其他片内资源只用于补充硬件层级背景。

资源表和图后说明按以下方式处理：

- GM：说明计算内存和通信内存均位于 GM，通信内存承载跨端传输的源数据和目的数据。
- L2 Cache：说明远端写请求通过访问校验后写入目标 GM 地址对应的 L2 Cache，L2 Cache 与 GM 的一致性由硬件维护。
- UB：说明通算融合时，AI Core 的计算结果先通过 UB 搬到 GM 通信内存后再参与跨端传输；收到的数据也可以从 GM 搬入 UB 继续计算。
- AI Core 和 AICPU 寄存器：不再展开作用、生命周期或编程方式。
- Memory Slice：在总览中直接建立与 `CcuBuffer` 的对应关系，为后文的 CCU 片上内存模型做准备。
- CCU 寄存器：只概括其保存通信参数和同步状态的作用，具体机制在后文展开。

L2 Cache 和 UB 的说明控制在各一个短段落内，不再介绍缓存模型、任务控制信息、完成状态或通信队列等内容。

建议使用以下表述：

> 远端写请求通过访问校验后，写入目标 GM 地址对应的 L2 Cache。L2 Cache 与 GM 之间的数据一致性由硬件维护。

> 在通算融合过程中，AI Core 的计算数据通过 UB 在计算单元与 GM 之间搬运。计算结果需要参与通信时，先从 UB 搬到 GM 中的通信内存；通信数据到达本端 GM 后，也可以搬入 UB 继续计算。

### 4.2 统一通信内存的控制面处理

删除以下内容：

- “通信内存有两种来源”的引导语。
- HcclBuffer 和用户注册通信内存的两个项目。
- 两类内存由谁申请、管理以及用户是否参与准备的对比。
- “对于 HcclBuffer”和“对于用户提供的 GM”的分支说明。

通信内存开头改为统一的概念说明：

> 通信内存在物理上位于 GM，是经过控制面准备、能够作为通信操作数并可向对端开放的内存范围。
>
> 通信开始前，控制面记录该内存的起始地址、大小和有效范围，按照通信协议完成内存注册并建立访问凭据。建立 Channel 时，控制面确定该 Channel 可以使用的通信内存，并向对端交换远端访问所需的内存描述和访问凭据。完成这些准备后，该段内存具备远端可见性，数据面可以依据 Channel、访问地址和凭据执行通信操作。

该表述统一覆盖不同的内存准备入口。具体由谁申请 GM、用户是否需要显式调用注册接口，以及内存如何释放，统一下沉到相应接口章节。

“远端可见性”小节继续展开注册、Channel 和信息交换的关系，但删除与通信内存来源有关的重复说明。

### 4.3 同步修改通信内存流程图

现有 `communication_memory_flow.png` 左侧明确区分 HcclBuffer 和用户 GM，与新的统一概念不一致，需要同步重画。

建议删除“通信内存来源”分区和两条分支，将流程统一为：

```text
一段 GM 内存
    -> 控制面记录有效范围并完成内存注册
    -> 按协议建立访问凭据
    -> 建立 Channel 并确定可使用的通信内存
    -> 交换内存描述和访问凭据
    -> 建立远端可见性
    -> 非对称内存 / 对称内存
```

图中只表达控制面完成的共同准备过程，不呈现具体内存申请接口或实现对象。修改时应保留 Draw.io 源文件，并在确认后导出同名 PNG 替换现有图片。

### 4.4 将后半部分重组为 CCU 片上内存模型

删除独立的 `L2 Cache`、`Unified Buffer` 和通用“寄存器”章节，将 Memory Slice 与 CCU 寄存器共同纳入新的 `CCU 片上内存模型` 章节。

建议在通信内存章节结束后增加以下转场：

> 上文介绍的通信内存位于 GM，用于承载跨端传输的源数据和目的数据，并通过内存注册、Channel 和访问凭据建立远端访问条件。CCU 执行通信任务时，还会使用片上的 `CcuBuffer` 和寄存器：`CcuBuffer` 用于暂存、中转和归约数据，寄存器用于保存搬运参数和同步状态。下面说明这两类片上资源如何与 GM 中的通信内存配合。

该转场建立以下递进关系：

```text
GM 通信内存
    -> 提供跨端访问的数据范围
    -> CCU 在本端发起数据搬运
    -> CcuBuffer 暂存、中转或归约数据
    -> CCU 寄存器提供地址、访问参数和同步状态
```

### 4.5 调整 CcuBuffer 章节

将当前 `Memory Slice` 标题改为 `CcuBuffer`。首段先说明物理资源和编程抽象之间的关系：Memory Slice 是 CCU 内部的片上存储资源，CCU 编程模型将其抽象为 `CcuBuffer`。

后续保留现有三类数据路径：

- 本端 GM 与本端 `CcuBuffer` 双向搬运。
- 本端 CCU 将对端 GM 数据读入本端 `CcuBuffer`。
- 本端 CCU 将本端 `CcuBuffer` 数据写入对端 GM。

继续保留必要的能力边界：跨端搬运由持有 `CcuBuffer` 的本端 CCU 发起，对端不能直接将其 GM 数据写入本端 `CcuBuffer`。

保留 `CcuBuffer` 在集合通信中暂存和归约中间数据的作用，具体分配和算子操作下沉到 CCU 接口及算子实现章节。

### 4.6 调整 CCU 寄存器章节

将当前 `CCU 寄存器` 小节移动到 `CCU 片上内存模型` 下，与 `CcuBuffer` 并列。保留三类寄存器的职责：

- 地址寄存器保存 GM 搬运地址。
- 通用寄存器保存地址、`Token`、数据长度等通信参数。
- 同步寄存器记录数据搬运完成、任务依赖满足和对端通知到达等事件。

保留 CCU 通过 Channel 传递地址、`Token` 和通知事件的机制，并明确该过程是 CCU 算子编排方式。用户通信数据仍通过 GM 与 `CcuBuffer` 相关的数据路径传输，寄存器传递的是通信参数和同步状态。

## 5. 方案合理性评估

### 5.1 总体结论

本方案整体合理，建议按此方案修改主文档。调整后的结构更符合编程模型章节的位置：先建立用户理解跨端访问所必需的通信内存概念，再介绍具有独立通信编程意义的 CCU 片上资源；缓存、计算寄存器和具体接口生命周期则只保留必要背景或下沉到对应章节。

本次调整改变的是概念组织和内容层级，不改变底层支持的内存来源、通信协议、数据通路或 CCU 能力。

### 5.2 统一通信内存概念是合理的

从底层资源管理看，通信组件管理的缓冲区和用户注册内存仍然具有不同的申请、登记和释放路径。通信内存管理代码分别保存内置通信缓冲区和用户注册的内存句柄，并在准备通信资源时汇总地址、大小、内存类型和标识等信息。Channel 和数据面最终使用的是已经准备好的内存描述、地址范围及协议凭据。

因此，编程模型章节可以将二者统一抽象为“经过控制面准备的 GM 通信内存”，原因如下：

- 用户理解远端访问时，需要关注的是有效地址范围、Channel 和访问凭据，而不是内存最初由哪个接口申请。
- 两类内存的差异主要影响资源生命周期和接口调用顺序，适合在接口或算子实现章节说明。
- 去除 HcclBuffer 名称可以避免用户在文档前部误以为它是一种独立物理内存或独立通信模型。

统一上层概念不等于声明两类内存的底层处理完全相同。正文应使用“控制面完成内存注册和通信准备”，不应写成“用户必须显式注册所有通信内存”。这样既能覆盖控制面自动准备的内存，也能覆盖由上层接口触发注册的 GM 内存。

### 5.3 收缩 L2 Cache、UB 和计算寄存器章节是合理的

L2 Cache、UB、AI Core 寄存器和 AICPU 通用寄存器在内存层级图中有助于建立硬件位置概念，但它们不需要在本文形成与通信内存并列的完整编程模型：

- L2 Cache 是目标 GM 访存路径上的硬件缓存层，不是用户独立选择的通信操作数。说明远端写与 L2 Cache、GM 的关系即可。
- UB 在通算融合中衔接 AI Core 计算和 GM 通信内存。保留数据经 UB 与 GM 搬运的关系，已经足以解释它在通信路径中的作用。
- AI Core 和 AICPU 寄存器服务于各自执行引擎，当前通信内存主线不依赖其分配、生命周期和使用方式。

将这些资源保留在总览而不设置独立章节，可以减少文档在通信内存之后重新发散到通用硬件资源的问题。现有内存层级图可以继续保留，但图注需要明确后文的展开范围。

### 5.4 将 CcuBuffer 和 CCU 寄存器合并介绍是合理的

CCU 编程模型将片上 Memory Slice 抽象为 `CcuBuffer`，同时将通用寄存器、地址寄存器和同步寄存器抽象为可编程资源。现有 CCU 能力说明还明确包含以下路径和操作：

- 本端 GM 与 `CcuBuffer` 之间的数据搬运。
- 对端 GM 与本端 `CcuBuffer` 之间由本端 CCU 发起的数据搬运。
- 本端 GM 与寄存器之间的参数加载和保存。
- 通过 Channel 写对端通用寄存器或同步寄存器。
- 使用本地事件和远端通知协调任务顺序。

`CcuBuffer` 负责数据暂存、中转和归约，寄存器负责地址、访问参数和同步状态。二者共同支撑 CCU 通信任务，将它们放在“CCU 片上内存模型”下连续介绍，与底层资源抽象和数据路径一致。

### 5.5 新的章节递进关系是合理的

调整后的正文形成以下递进：

```text
内存资源总览
    -> GM 中哪些范围可以参与通信
    -> 如何建立远端可见性和访问授权
    -> 用户如何组织和寻址通信内存
    -> CCU 如何使用片上资源处理这些通信数据
```

这条主线先回答“通信数据在哪里以及如何访问”，再回答“CCU 使用哪些片上资源处理这些数据”。与当前从通信内存突然切换到 L2 Cache、UB 和多类寄存器相比，主题更集中，转场也更自然。

为了避免通信内存与 CCU 片上资源混为一类，正文仍需明确以下边界：

- 通信内存位于 GM，承载跨端传输的源数据和目的数据。
- `CcuBuffer` 位于 CCU 片上，供本端 CCU 暂存、中转和归约数据；其跨端路径由持有该资源的本端 CCU 发起。
- CCU 寄存器传递地址、`Token`、数据长度等通信参数和同步状态，批量用户数据仍通过 GM 或 `CcuBuffer` 相关路径传输。

### 5.6 实施风险及控制方式

| 风险 | 控制方式 |
| --- | --- |
| 去除 HcclBuffer 后，用户不了解不同内存准备入口的差异 | 在通信内存章节末尾指向接口章节，由接口章节说明申请、注册和释放方式 |
| “内存注册”被理解为所有场景都要求用户显式调用注册接口 | 使用“控制面完成内存注册和通信准备”，不把注册动作固定为用户操作 |
| L2 Cache 与 GM 一致性被理解为通信已经完成 | 总览只说明数据写入路径和硬件一致性，不据此推导通信完成或执行同步 |
| UB 被理解为可直接参与跨端传输 | 明确计算数据先在 UB 与 GM 之间搬运，跨端数据仍由 GM 中的通信内存承载 |
| 内存层级图仍展示 AI Core 和 AICPU 寄存器，正文却不展开 | 在图注中说明这些资源用于展示硬件层级，本文只展开通信内存和 CCU 片上资源 |
| 旧通信内存流程图仍按两种内存来源分支 | 正文修改时同步更新流程图；图片未更新前不合入新的通信内存表述 |
| `CcuBuffer` 被理解为可以由对端直接访问的通信内存 | 保留三类支持路径，并明确跨端搬运由本端 CCU 发起以及对端不能直接写入 `CcuBuffer` |

### 5.7 评估结论

方案在概念层级、章节重点和底层能力对应关系上均成立。实施时满足以下三个条件即可保持准确性和完整性：

1. 统一通信内存概念时保留底层入口和生命周期存在差异这一边界，并将差异下沉到接口章节。
2. 正文与 `communication_memory_flow.png` 同步修改，避免文字和图片采用不同分类方式。
3. 将 L2 Cache 和 UB 收入总览后，继续保留其与 GM 通信数据路径的最小必要关系。
